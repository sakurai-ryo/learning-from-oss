## 軸

**1 本の SQL の一生を、接続層から InnoDB のディスクまで縦に下る。**

アプリケーションエンジニアが MySQL について知っていることの大半は「現象」だ。デッドロックが出る、ALTER が固まる、レプリカが遅れる、インデックスがあるのに使われない。この章はそれらの現象を起点にはせず、SQL が通る層を上から順に読む。接続を受け付けるスレッド、パケットを解釈するプロトコル層、Bison パーサ、コストベースオプティマイザ、iterator エグゼキュータ、handler という Server と InnoDB の境界、そして InnoDB の中で B+tree・バッファプール・トランザクション・ロック・redo・purge がどう協調するか。各ページの「どう活かすか」で、その層が原因になる現象に結びつける。最後の群に症状から引く索引を置いて、逆引きもできるようにする。

InnoDB の説明は REPEATABLE READ (InnoDB 既定) を基準に書き、READ COMMITTED で何が変わるかを該当ページで毎回注記する。

ページの形は 2 種類を混ぜる。層ごとに architecture walkthrough を 1 枚置いて配線と制御フローを固定し (下表で `W`)、設計理由は lesson ページに切り出す (`L`)。walkthrough は 13 枚。

## 対象外

- Group Replication (`plugin/group_replication/`)、InnoDB Cluster、MySQL Router (`router/`)
- コンポーネント基盤 (`components/`)、プラグイン API 一般 (X Plugin と semisync は個別に読む)
- イベントスケジューラ、ストアドプログラムの実行エンジンの内部 (`sp_head` / `sp_instr` の命令セット。群 6.5 では文脈の凍結とキャッシュだけ扱う)
- 権限・認証の ACL (`sql/auth/` は握手部分だけ読む。ビューとストアドプログラムの DEFINER は群 6.5 で扱う)
- 全文検索 (`storage/innobase/fts/`)、空間インデックス (`gis/`、`lock0prdt.cc`)、ページ圧縮・暗号化・keyring、クローンプラグイン
- X DevAPI のドキュメントストア (コレクション、`mysqlx_*` の CRUD は SQL への変換までで止める)
- MyISAM・MEMORY・NDB などの他エンジン (TempTable は内部一時表として読む)、Enterprise thread pool
- CTE・ウィンドウ関数の機能単位ページ (エグゼキュータのページで触れるだけ)
- hypergraph オプティマイザの内部 (対比 1 ページのみ。8.4 では release ビルドで有効化できない)
- 旧 `libbinlogevents/` (8.4.11 では `libs/mysql/binlog/event/` への転送スタブ)

## 確認済みの要点 (8.4.11 で名前や場所が想定と違うもの)

執筆時に検索で空振りしやすいものを先に書いておく。

- `mysql_parse` は `dispatch_sql_command` に改名 (`sql_parse.cc` L5275)。`do_command` は classic protocol であることを assert する。X Plugin は `command_service_run_command` で再入する
- `Protocol_classic::send_result_set_metadata` はない。メタデータは `start_result_metadata` / `send_field_metadata` / `end_result_metadata` の 3 段。本物の `send_result_set_metadata` は `Query_result` (`sql/query_result.h` L124)
- `COM_*` は `include/my_command.h`、`SERVER_STATUS_*` と capability flag は `include/mysql_com.h`
- クライアント API の本体は `sql-common/client.cc` (9645 行)。`libmysql/libmysql.cc` は prepared statement 側。サーバも `client.cc` をリンクする (receiver thread 用)
- `Table_ref` (旧 `TABLE_LIST`) は `sql/table.h` L2865。`sql/sql_lexer` は存在せず lexer は `sql/sql_lex.cc` + `sql/lex.h`
- `Query_block::resolve_subquery` はない。`resolve_placeholder_tables` と scalar subquery → derived の変換
- `sql/opt_range.cc` はない。`sql/range_optimizer/` に分割済みで、partition pruning も `partition_pruning.cc` にある
- `JOIN::exec` はない。実行の入口は `Query_expression::ExecuteIteratorQuery` (`sql/sql_union.cc` L1688)
- `MaterializeIterator` / `TemptableAggregateIterator` は `composite_iterators.cc` 内の private template で、factory 関数だけ公開
- `merge_many_buff` は `sql/merge_many_buff.h` の header-only template
- `TC_LOG` は `sql/tc_log.h`
- InnoDB: `btr_cur_search_to_nth_level` は 8.4 でも free function (method 化されたのは `btr_pcur_t` だけ)。`trx_assign_id_for_rw` は存在せず `trx_sys_allocate_trx_id`
- InnoDB: record header 定数は `storage/innobase/rem/rec.h` (private header)、page header offset は `include/page0types.h`、`TRX_ISO_*` は `include/trx0trx.h`、checksum は `buf/checksum.cc`。`rec_needs_ext` はなく `page_zip_rec_needs_ext` が全行フォーマット共通
- InnoDB: RC でギャップロックを省く判定は `row/row0ins.cc` L1449 と `ha_innodb.cc` にあり、`lock0lock.cc` を grep しても出ない
- InnoDB: `page_cleaner_flush_pages_recommendation` は消え、adaptive flushing は `set_flush_target_by_lsn` (`buf0flu.cc` L2497)

## 確認済みの要点 (docs に書かれにくい挙動)

- `check_and_incr_conn_count` は `max_connections + 1` まで通し、admin 予約の判定は認証中の `valid_connection_count()` で行う
- `wait_timeout` はタイマースレッドでなく、`do_command` が毎コマンド `my_net_set_read_timeout` で socket read timeout を張り直す
- thread cache で pthread は再利用されるが、`handle_connection` は毎回新しい THD と PFS thread を作る (`thread_id` は変わり pthread は変わらない)
- `CLIENT_DEPRECATE_EOF` では `send_eof()` が OK パケットを送る。`COM_BINLOG_DUMP(_GTID)` だけ本物の EOF
- caching_sha2_password の fast / full の切替は 1 バイトのパケット (`\3` / `\4`)。RSA fallback で非 TLS の初回接続だけ往復が増える
- サーバ側カーソルは materialize のみ (`Materialized_cursor`)。`mysql_use_result` は結果を読み切るまで同じ `MYSQL*` で次のコマンドを送れない
- LOAD DATA LOCAL はサーバが `net_request_file` を送り、クライアントがファイルを流す。安全境界はクライアント側
- X Protocol のフレーム長は type バイトを含む。payload 0 は拒否、上限超過は切断。X Plugin は独自 executor を持たず `srv_session_open` + `COM_QUERY` で classic と同じ `dispatch_command` に合流する。ワーカーは `mysqlx_min_worker_threads = 2` の動的プール
- 構文エラーはセッション状態を変えない: Bison アクションは THD に触らず `PT_*` を作るだけ、`parse_sql` は parser 用の Diagnostics_area を一時的に差し替える
- ダイジェストは lexer 内で SHA-256、`character_set_client` 込みで別の値になる
- `opt_statistics.cc` は 120 行で関数 1 つ。カーディナリティ推定はほぼ `records_in_range` + `rec_per_key`
- `optimizer_switch` は 28 フラグだが help 文に `hypergraph_optimizer` / `use_invisible_indexes` / `subquery_to_derived` は出ない。`batched_key_access` は既定 off
- hash join の spill は最大 128 chunk (`kMaxChunks`)。`max_length_for_sort_data` は deprecated で無効。`temptable_max_mmap` 既定 0
- `handler` の virtual で pure なのは `rnd_init` / `rnd_next` / `info` の 3 つだけ。非 pure は `HA_ERR_WRONG_COMMAND` を返す
- `dict_sys_t::s_dd_space_file_name = "mysql.ibd"` はツリー内で唯一の出現。I_S テーブルは DD 上の SQL view として bootstrap 時に生成される
- MDL は 8.4 で partition を持たず単一の `LF_HASH`。`sql_alter.cc` は 449 行で、ALGORITHM / LOCK の決定はほぼ `handler0alter.cc` (11321 行) 側。`copy_data_between_tables` は宣言 L454、定義 L18620
- instant DDL は 8.0.13 の instant cols と 8.0.29 の row versions の 2 機構が併存し、同じテーブルで両方立たないことを assert
- InnoDB: extent は 1MB / page_size なので「64 ページ」は 16KB の時だけ。root ページは動かない (`btr_root_raise_and_insert`)
- InnoDB: read-only トランザクションは `trx->id == 0`。read view は pool から再利用。`changes_visible` は 3 分岐 + `binary_search`
- InnoDB: デッドロック検出は `lock_wait_timeout_thread` の周期的な仕事で、待つ側のスレッドでは行わない。`lock_sys` は table / page 各 512 shard
- InnoDB: `lsn` と `sn` は別の数直線 (LSN は block header を飛ばす)。`MLOG_*` に `_8027` の互換 variant がある。redo capacity は 8MB〜512GB
- InnoDB: LRU の midpoint 分割は 512 ブロック未満で無効。doublewrite のファイル名にページサイズが入る。O_DIRECT は実行時に一時ファイルで probe する
- InnoDB: `innodb_fatal_semaphore_wait_threshold` の半分で `buf0buf.cc` / `dict0stats.cc` / `fts0fts.cc` が自主的に抑制する
- binlog: ordered_commit は 5 つの stage ID を持つ。`AFTER_COMMIT_STAGE` は semisync の `after_commit` を別 mutex で回すためだけにある。`binlog_group_commit_sync_delay` は `sync_binlog` 周期に達したときだけ効く
- binlog: FDE の `post_header_len[]` が前方互換の実体。`Transaction_payload_log_event` (zstd) は展開しないと中の Table_map / Rows が見えない
- semisync: AFTER_SYNC は commit stage の mutex を持ったまま `ha_commit_low` の前で待つ。止まった replica は待っているセッションだけでなく commit pipeline 全体を止める。ACK は専用スレッドが集める
- レプリ: `Seconds_Behind_Source` は `last_master_timestamp == 0` なら 0 を返す (NULL ではない)。MTA では GAQ 退出時にしか進まない
- 観測: EXPLAIN FORMAT=TREE と EXPLAIN ANALYZE は FORMAT=JSON と同じ `Json_object` の rendering。`TimingIterator` は行ごとに `steady_clock::now()` を 2 回呼ぶ。`optimizer_trace` は上限超過で切り詰め (破棄ではない)。`performance_schema.data_locks` は読むたびに InnoDB の latch を取る
- テスト: `DBUG_EXECUTE_IF` の中で `DEBUG_SYNC` を仕込む合成が多用される。`ut_ad` は release で空になるので release と debug は別のプログラム

## つまずきどころ候補 (該当ページに散らす)

- `SELECT` だけの長いトランザクションが MDL で ALTER を止め、ALTER が後続の全クエリを止める (79)
- RR で最初の `SELECT` を打った瞬間にスナップショットが固定される。RC は文ごと (59)
- `INSERT ... ON DUPLICATE KEY UPDATE` や UNIQUE 重複での next-key lock によるデッドロック (63)
- デッドロック検出が周期的なので `innodb_lock_wait_timeout` (既定 50s) に先に当たることがある (64)
- `instant` は 64 回で rebuild が必要 (81)。`ERROR 1799` は `innodb_online_alter_log_max_size` (82)
- `tmp_table_size` はテーブル単位、`temptable_max_ram` はグローバル (37)
- `mysql_use_result` / ストリーミング中は同じ接続で別のクエリを送れない。mysql2 の `stream()` も同じ (17)
- `max_allowed_packet` はサーバとクライアント両方の値が効く (14)
- `Seconds_Behind_Source` の 0 は「追いついた」とは限らない (91)
- `binlog_row_metadata=MINIMAL` (既定) では Table_map に列名がない (85)
- `innodb_change_buffering` が 8.4 で OFF になっているので 8.0 のチューニング記事が当てはまらない (75)
- `I_S.INNODB_LOCK_WAITS` を前提にした古い手順が動かない (96)
- Aurora では redo / doublewrite / page cleaner のページの前提が成り立たない (99)

## 執筆中に判明した計画の誤り (上の表より優先)

執筆時に 8.4.11 タグで実読して分かった、上の表・「確認済みの要点」の誤り。**表と食い違ったらこちらを採用する。**

- `handler` の pure virtual は 3 個ではなく **12 個** (`rnd_next` / `rnd_pos` / `position` / `info` / `table_type` / `index_flags` / `store_lock` / `open` / `close` / `rnd_init` / `table_flags` / `create`)。ただし「書き込み系とインデックス走査は非 pure で `HA_ERR_WRONG_COMMAND` を返す」は正しい (既定実装は 27 箇所)
- 隠し列は常に 13 バイトではない。`DB_TRX_ID` 6 + `DB_ROLL_PTR` 7 = 13 が常時で、`DB_ROW_ID` 6 が加わって 19 になるのは**クラスタリングキーが一意でないとき**だけ (`dict0dict.cc` L3192 の `if (!dict_index_is_unique(index))`)
- `prune_partitions()` は 2 経路から呼ばれる。`JOIN::optimize` からのほかに `Query_block::prepare` (`sql_resolver.cc` L870) から定数条件のみで先に呼ばれる
- `AccessPath::Type` は 41 種ではなく **46 種** (`access_path.h` L229-288)
- `Filesort_buffer` は `sql/sql_sort.h` ではなく `sql/filesort_utils.h` L81。`sql_sort.h` にあるのは `MERGEBUFF` / `MERGEBUFF2` / `Merge_chunk`
- `MaterializeIterator` は `composite_iterators.cc` の無名名前空間の中、`TemptableAggregateIterator` は名前空間なしでヘッダに出していないだけ。隠し方が違う
- `lex.h` の `symbols[]` はソートされているが引くのはハッシュ。実体は `sql/gen_lex_hash.cc` が生成する完全ハッシュ。エントリは 823 個の 1 本の配列 (`SG_*` フラグで関数と予約語を区別)

- ダイジェストのハッシュに `character_set_client` は**入らない**。`compute_digest_hash` はトークン配列だけを SHA-256 に通す。`m_charset_number` は `DIGEST_TEXT` の utf8mb3 変換用。「同じ文字列でも別ダイジェスト」になるのは識別子に非 ASCII バイトを含む場合だけ
- PFS のダイジェストキーは「スキーマ名 + ハッシュ」(`PFS_digest_key`)。デフォルトスキーマが違えば別行
- `RIGHT JOIN` は contextualize の冒頭 (`PT_joined_table::contextualize_tabs`) で `LEFT JOIN` に書き換えられ左右が入れ替わる。以降の層は `RIGHT JOIN` を知らない
- `ER_WARN_INDEX_NOT_APPLICABLE` は `EXPLAIN` か `sql_safe_updates` のときしか積まれない
- `agg_item_charsets` の比較文脈と文字列結果文脈の差は 3 点。`MY_COLL_ALLOW_NUMERIC_CONV`、`MY_COLL_DISALLOW_NONE`、`only_consts`。3 つ目 (比較では定数にしか変換器を挿さない = 列を包まない) がインデックス可否の核心
- `hash_join_iterator.h` の `kMaxChunks = 128` の理由は fd 枯渇防止 (コメントに明記)
- `Using join buffer (hash join)` の判定は `setup_join_buffering` (`sql_optimizer.cc` L3495)。内側の `type` が `ALL` / `index` / `range` / `index_merge` なら hash join、`ref` / `eq_ref` なら BKA 候補

- `LIKE '%abc'` は「range にならない」のではない。`my_like_range_*` は先頭 `%` でも min を `\0`、max を `max_sort_char` で埋めた**インデックス全体を覆う区間**を作る。失敗するのは不正マルチバイト列のときだけ。正確には「常にコストで負ける range にしかならない」

- `sql_derived.cc` L1102 は `can_push_condition_to_derived` (L1099)。merge / materialize の判断は `Query_block::merge_derived` (`sql_resolver.cc` L3344) と `Query_expression::is_mergeable` (`sql_lex.cc` L3962)
- `Cost_model_server` は `opt_costmodel.h` L54 だが、既定値を持つ `Server_cost_constants` は `opt_costconstants.h` L65 (ctor L79)

  - `innodb_read_io_threads` = `clamp(hardware_concurrency()/2, 4, 64)` (8.0 は 4 固定)

  - `innodb_change_buffering` = `none` (OFF)

  - `innodb_page_cleaners` は宣言上 1 だが起動時にインスタンス数へ合わせられる
  - `innodb_flush_method` を明示しないと `os_is_o_direct_supported` の probe 結果で決まるので、**8.4 では O_DIRECT が事実上の既定**
- バッファプールのインスタンス割当は round-robin ではなく**ハッシュ** (`buf_pool_get`、`buf0buf.ic`)。`page_no >> 6` を落としてから `hash() % instances` なので**連続 64 ページは同じインスタンス**に載る。round-robin なのは `buf_block_alloc` の作業用ブロックだけ
- adaptive flushing の構成は `Adaptive_flush::page_recommendation` → `set_flush_target_by_lsn` + `set_flush_target_by_page`。`sum_pages_max = srv_max_io_capacity * 2` は「書く枚数」ではなく **flush list を数える枚数の上限**
- `read_ahead_area` = `min(64, ut_2_power_up(curr_size / 32))`。64 に届くのは 1 インスタンス 1056 ページ (約 16.5MB) 以上から
- **`innodb_fill_factor` は通常の INSERT に効かない**。`ddl::fill_factor` を読むのは `btr0load.cc` と `btr0mtib.cc` (bulk load) だけ。通常挿入の余白は `dict_index_get_space_reserve()` = `UNIV_PAGE_SIZE / 16` 固定で、しかも連番挿入と判定されたときにしか効かない
- `FSEG_FRAG_ARR_N_SLOTS` / `FSEG_FRAG_LIMIT` は `fsp0types.h` ではなく `fsp0fsp.h` (L218 / L248)
- `struct ref_t` 本体は `lob0lob.h` L198 (計画の L102-115 は `BTR_EXTERN_*` 定数)。`length()` は 8 バイトのうち**下位 4 バイトしか読まない** (`lob::MAX_SIZE = UINT32_MAX`)
- `REC_MAX_N_USER_FIELDS = 1017` (= `REC_MAX_N_FIELDS - DATA_N_SYS_COLS * 2`)。「1 テーブル 1017 列」の出所で、超過は `HA_ERR_TOO_MANY_FIELDS`
- `btr_cur_optimistic_delete` の実名は `btr_cur_optimistic_delete_func`
- `Row size too large (> 8126)` の 8126 は `page_get_free_space_of_empty(true) / 2` = `(16384 - 120 - 8 - 4) / 2`。64KB ページのときだけ `REC_MAX_DATA_SIZE - 1 = 16383` に切り替わる
- `log_writer_wait_on_consumers` は archiver / clone 用ではない。8.4.11 では待ちが 3 種に分かれている: `log_writer_wait_on_checkpoint` / `log_writer_wait_on_archiver` / `log_writer_wait_on_consumers` (後者は MEB 用で `ut_ad(name == "MEB")`)
- mtr の `oldest_modification` は「mtr **開始時**の LSN」ではない。LSN 割当は `mtr_t::Command::execute()` 内の `log_buffer_reserve`、つまり commit 時。正しくは「その mtr の redo レコード群の開始 LSN」。かつ**既に dirty なページでは更新されない**
- クラッシュリカバリの順序は「DD open → binlog recovery → undo rollback」。`mysqld.cc` の実際の順は `dd::init` → `tc_log->open` (binlog recovery) → `ha_post_recover` → `log_ddl->recover` → rollback スレッド起動。**binlog recovery が undo rollback より先**
- redo 逼迫時のエラー文言は `Log writer is waiting for checkpoint` ではない。実在するのは `Redo log is running out of free space, pausing user threads...` / `Out of space in the redo log. Checkpoint LSN: %llu.` / `Threads are unable to reserve space in redo log...` / `Redo log writer is waiting for %s redo log consumer...`
- doublewrite のファイル本数は `innodb_doublewrite_files` (既定 2)。`max(4, buf_pool_instances * 2)` はセグメント数であってファイル数ではない
- チェックポイント LSN は 3 つの min: `min(buf_pool_get_oldest_modification_lwm(), recent_closed.tail(), flushed_to_disk_lsn)`。3 つ目がないとデッドロックする旨がコメントにある
- X Plugin は「イベントループ + ワーカープール」ではない。`Socket_events::loop()` に登録されるのは listen ソケットとタイマーだけで、確立済み接続は登録されない。accept 後は `Client::run` が接続の一生ぶんワーカースレッドを占有する。classic との違いは供給が固定 thread cache でなく動的プールである点だけ
- `thread_cache_size` の既定は `sys_vars.cc` の `DEFAULT(0)` ではなく、`mysqld.cc` L6723 で `8 + max_connections/100` (上限 100) に自動設定される
- `mysql_native_password` は 8.4 で `PLUGIN_OPT_DEFAULT_OFF`。`default_authentication_plugin` は削除され `authentication_policy` (既定 `"*,,"`) に置き換わった
- `compress_packet` の定義は `net_serv.cc` L1255 (L104 は前方宣言)。`mysql_use_result` L9486 は委譲だけで本体は `cli_use_result` (L8347)
- **`innodb_adaptive_hash_index` の既定は 8.4 で OFF** (`ha_innodb.cc` の `MYSQL_SYSVAR_BOOL` 最終引数が `false`)。ヘルプ文だけ "enabled by default" のまま残っている
- **`srv_threads_t` という型は存在しない。** 実体は `struct Srv_threads` (`srv0srv.h` L165)
- `Innodb_ibuf_*` ステータス変数は upstream MySQL に元から存在しない (Percona Server の拡張)。「8.4 で消えた」ではない
- `innodb_fatal_semaphore_wait_threshold` の自主抑制は `buf0buf.cc` / `dict0stats.cc` が `threshold / 2`、`fts0fts.cc` は `threshold * 0.98`。長い semaphore 待ちの**警告**は `sync0arr.cc` のハードコード 4 分で、この変数とは別
- `innodb_purge_batch_size` は 300 (`srv0srv.cc` の `= 20` は plugin var に上書きされる C 初期化子)。`innodb_purge_threads` は固定 4 ではなく **CPU ≤ 16 なら 1、超なら 4**
- `innodb_max_purge_lag_delay = 0` は遅延を**無効化**する。`innodb_max_purge_lag` だけ設定しても何も起きない
- AHI のパーティション選択は `hash(space_id, index_id) % btr_ahi_parts`。**1 本のインデックスは必ず 1 パーティションに固定される**ので、`innodb_adaptive_hash_index_parts` を上げてもホットな単一インデックスの latch 競合は割れない
- purge キューの要素は rseg で、**空だった rseg のときだけ push** される。`History list length` とキュー長は別物
- `unittest/gunit/innodb/` の単体テストは 4 本ではなく 18 本 (+ `lob/` に 1 本)。ただし「utility 層だけで B+tree やロックの単体テストは存在しない」という主張自体は正しい (`ha_innodb-t.cc` は 98 行で `innobase_convert_name` 1 つだけ)
- `t/*.test` の 1460 は `mysql-test/t/` 直下 (main スイート) の数。ツリー全体では 8982 本。`suite/` は 61 個だが既定で走るのは `@DEFAULT_SUITES` の 38 個だけ
- `UNIV_DEBUG` は `WITH_DEBUG` が直接定義するのではなく、`WITH_DEBUG` → `CMAKE_BUILD_TYPE=Debug` → `innodb.cmake` が `CMAKE_CXX_FLAGS_DEBUG` に `-DUNIV_DEBUG` を足す 2 段
- **`DEBUG_SYNC` は debug ビルドでも既定では動かない。** `--debug-sync-timeout` を渡さないと `opt_debug_sync_timeout == 0` でマクロが即抜ける。MTR は既定で有効化する
- `ut_ad` の定義は `ut0dbg.h` L103-133 (L93 は `ut_a`)
- `mysqltest.cc` の `check_result` には hypergraph 専用の逃げ道があり、無視してよい差分なら fail ではなく `abort_not_supported_test("Hypergraph optimizer did not support all queries.")` になる
- Aurora の `innodb_flush_log_at_trx_commit` はバージョンで意味が違う (v2 は 0/2 が待たない、v3 は 0 のみ。v3 では `innodb_trx_commit_allow_data_loss=1` が前提)
- **`lock_rec_has_to_wait` は 8.4 に存在しない。** 互換性判定の本体は `locksys::rec_lock_check_conflict` (`lock0lock.cc` L553)、呼ぶのは `rec_lock_has_to_wait` (L653)
- `trx_sys_allocate_trx_id` は `trx0sys.cc` ではない。宣言 `include/trx0sys.h` L134、定義 `include/trx0sys.ic` L258 (実体は `trx_sys_allocate_trx_id_or_no`)
- RR/RC の read view の差は `row0sel.cc` にない。`trx_assign_read_view` (`trx0trx.cc` L2319) は分離レベルを見ておらず、差は `ha_innobase::store_lock` と `external_lock` の `view_close` 2 箇所だけで作られる
- `row0ins.cc` L1449 の `skip_gap_lock` は**外部キー検査**であって重複検査ではない。重複検査 (L1967) は `dict_table_t::skip_gap_locks()` = DD/SDI テーブル判定のみで分離レベルを見ない。RR/RC の分岐の中心は `trx0trx.h` L1109-1131 の 4 述語 (`skip_gap_locks` / `allow_semi_consistent` / `releases_non_matching_rows` / `releases_gap_locks_at_prepare`)
- `trx_weight_ge` の定義は `trx0trx.cc` L2899 (`lock0wait.cc` L949 は呼び出し側)
- **`INSERT ... ON DUPLICATE KEY UPDATE` と `REPLACE` の重複検査は S ではなく X を取る** (`row_allow_duplicates` 分岐)。素の `INSERT` が `LOCK_S`
- **「デッドロック検出は周期的なので先に `innodb_lock_wait_timeout` に当たる」は誤り。** 待ち手が `lock_wait_table_reserve_slot` でスロットを取った時点で `lock_wait_request_check_for_cycles()` がイベントをセットし、背景スレッドが即座に 1 周する。1 秒周期なのは**タイムアウト検査のほう**だけ。正しくは「検出は待ち手ではなく背景スレッドが行う非同期処理で、スナップショットが古ければ次周に回る」
- RC の追加差分: `INSERT ... SELECT` の読み側がロックなしになる (`start_stmt`)、`HA_BINLOG_STMT_CAPABLE` が落ちて `ER_BINLOG_STMT_MODE_AND_ROW_ENGINE` になる、XA PREPARE でギャップロックを先に手放す (`trx_prepare`)
- **`alter_algorithm` システム変数は 8.4.11 に存在しない** (8.0.16 で削除)。残っているのは `old_alter_table` (`sys_vars.cc` L3108、SESSION_VAR)。ON だと `ALGORITHM=INPLACE/INSTANT` を明示しない限り強制 COPY
- **InnoDB は `HA_ALTER_INPLACE_NO_LOCK` を一度も返さない。** 最終行は `return online ? NO_LOCK_AFTER_PREPARE : SHARED_LOCK_AFTER_PREPARE;`。したがって online な INPLACE でも**排他 MDL の窓は 2 回開く** (prepare 直前と commit 直前)。**INSTANT も commit 前に X を取る**ので「INSTANT ならノーロック」は誤り
- 構築フェーズの MDL は SNW ではなく **SU**。`LOCK=SHARED` のときだけ SNW
- row log の適用は排他 MDL の下ではない。`row_log_apply` は `rw_lock_x_lock(dict_index_get_lock(index))` を取るだけで MDL は SU のまま
- **`REC_INFO_INSTANT_FLAG` (0x80) は 8.0.13 の instant cols 用。8.0.29 の row versions は別ビット `REC_INFO_VERSION_FLAG` (0x40)。** 計画はこの 2 つを混同していた。定義は `storage/innobase/rem/rec.h` L152。両立しない `ut_a` は `rem0rec.cc` L1094 と `row0upd.cc` L522
- `innodb_sort_buffer_size` は **row log 専用**で、8.0.27 以降の DDL ソートには使われない。構築側は `innodb_ddl_buffer_size` (THD 単位を `m_max_buffer_size / n_buffers` で分割)
- `ALTER INDEX ... INVISIBLE` は `fill_alter_inplace_info` が `RENAME_INDEX` を流用して立てるので INSTANT にならず INPLACE
- `INNODB_TABLES` の `INITIAL/CURRENT/TOTAL_COLUMN_COUNTS` は `#ifdef UNIV_DEBUG` でリリースビルドにない (`TOTAL_ROW_VERSIONS` は常にある)
- エラー番号: `ER_INNODB_ONLINE_LOG_TOO_BIG` = 1799、`ER_ALTER_OPERATION_NOT_SUPPORTED_REASON` = 1846、`ER_INNODB_MAX_ROW_VERSION` = 4092
- 「`Using temporary` / `Using filesort` だけは enum ではなく bool」は不正確。`ET_USING_TEMPORARY` / `ET_USING_FILESORT` は `Extra_tag` enum に実在する (全 35 タグ + `ET_total`)。特殊なのは**決定の出所**で、この 2 つだけがテーブルごとの `QEP_TAB` ではなくクエリブロック全体の `JOIN::explain_flags` を `any()` で 2 個の bool に潰し、`Explain_join` の `need_tmp_table` / `need_order` として渡される。階層フォーマットではそもそも出さない
- 「TREE と ANALYZE は FORMAT=JSON と同じ rendering」は既定では成り立たない。`explain_json_format_version` の既定は **1** で、この場合 `FORMAT=JSON` は旧来の `qep_row` ベース。`2` にするか hypergraph 有効時のみ iterator ベースになる。TREE と ANALYZE は常に iterator ベース
- **`SHOW ENGINE INNODB STATUS` の SEMAPHORES の spin/round/OS wait は 8.4 で全部ハードコードのゼロ** (`sync0sync.cc` に "deprecated and prints all 0 for compatibility")。latch 競合の判断に使えない
- `Handler_*` を加算するのはサーバではなくストレージエンジン (`ha_innodb.cc` の 11 か所が `ha_statistic_increment` を直接呼ぶ)
- `EXPLAIN ANALYZE` の `actual_rows` / `actual_*_ms` は **`num_init_calls` で割った 1 ループあたりの平均**。総行数ではない
- `data_locks` の `with_lock_data` は `true` 固定なので `LOCK_DATA` を SELECT しなくても毎回組み立てられる。ページがバッファプールになければ `NULL` になる
- `sys.schema_unused_indexes` は `NON_UNIQUE = 1` を要求するので **UNIQUE インデックスは絶対に出ない**
- `SHOW ENGINE INNODB STATUS` の 1MiB 超過時は TRANSACTIONS の**先頭** (古いもの) から削られる
- **`Binlog_commits` / `Binlog_group_commits` は MySQL に存在しない** (MariaDB のもの)。`status_vars[]` の binlog 系は `Binlog_cache_use` / `Binlog_cache_disk_use` / `Binlog_stmt_cache_*` の 4 つだけ。グループサイズを直接測る手段はなく、P_S の `LOCK_sync` / `LOCK_log` 待ちで代替する
- `Rpl_semi_sync_source_wait_timeouts` というステータス変数は存在しない。あるのは `status` / `clients` / `yes_tx` / `no_tx` / `wait_sessions` / `no_times` / `timefunc_failures` / `wait_pos_backtraverse` / `tx_*` / `net_*`
- `transaction_write_set_extraction` も 8.4 で削除済み。writeset 抽出は無条件・XXH64 固定。`binlog_transaction_dependency_history_size` (25000) は残っている
- `total_ha_2pc > 1` で飛ばすのは `ha_recover` だけで、XID スキャン自体は飛ばさない。スキャンを丸ごと省くのは `LOG_EVENT_BINLOG_IN_USE_F` が立っていないとき
- `mysql.gtid_executed` は binlog 有効時**ローテート時にしか書かれない**。`gtid_executed_compression_period` の既定は 8.0.23 以降 0 (無効)
- semisync の AFTER_SYNC は `binlog_order_commits=ON` のとき `LOCK_commit` を保持したまま待つ。**OFF のときは `LOCK_sync` を先に unlock してから呼ぶのでステージ mutex を持たない**
- レプリケーションフィルタの参照点はすべて**適用段**。relay log には全イベントが残るので、フィルタはネットワークもディスクも節約しない。`sequence_number` に穴も空かない

### 群 6.5 の執筆で分かったこと (2026-09-04)

- **厳格モードは `Field` の中では判定されない。** `Field::set_warning` も `Field::store` も `SL_WARNING` で積むだけで、`SL_ERROR` への昇格は `Strict_error_handler::handle_condition` が `level` ポインタを書き換えて行う。`push_warning` には `assert(severity != SL_ERROR)` があるので、警告として積む以外の道がない
- **`STRICT_TRANS_TABLES` と `STRICT_ALL_TABLES` の差は 1 つの述語だけ。** `!cannot_safely_rollback(STMT) || (sql_mode & MODE_STRICT_ALL_TABLES)`。InnoDB しか使っていなければ両者に差はない
- **`max_sort_length` は PAD SPACE の照合順序にしか効かない。** `sortlength` の `min` は `!sortorder->is_varlen` の枝の中にあり、NO PAD (8.0 既定の `utf8mb4_0900_ai_ci`) では `is_varlen` が立つので通らない
- **JSON のキー順は辞書順ではない。** `Json_key_comparator` は長さを先に比較し、同じ長さのときだけ辞書順にする (探索を速くするため)
- **外部キー検査は自前で RC を判定する。** `row_ins_check_foreign_constraint` の `skip_gap_lock = (trx->isolation_level <= TRX_ISO_READ_COMMITTED) || table->skip_gap_locks()`。群 10 で挙げた `trx0trx.h` の 4 述語とは別経路
- **一致した親行に取るのは `LOCK_S` + `LOCK_REC_NOT_GAP`。** RR でもギャップを取らない。ギャップを取るのは (1) 親が見つからなかったとき (2) 削除マーク付きの親に当たったとき (3) supremum に達したとき、の 3 つ
- **子側の索引を自動生成するのは SQL 層。** `dict_foreign_t` のコメントは `InnoDB does not generate new indexes implicitly` と書いているが、`prepare_foreign_key` に `we always add generated supporting key` とある
- **`foreign_key_checks` は `IN_BINLOG`。** 値がレプリカに伝わるので、検査を切って流した変更はレプリカでも検査されない
- **関数インデックスの隠し列名は `!hidden!<インデックス名>!<キーパート番号>!<連番>`。** 名前が長いとインデックス名の側だけが切り詰められる (連番を削ると衝突回避のループが終わらないため)
- **トリガは作成時の `sql_mode` と文字セット 3 種を凍結する。** `Trigger_creation_ctx` が `character_set_client` / `collation_connection` / データベースの照合順序を持ち、パース時に差し替えて戻す。パース中は `m_digest` と `m_statement_psi` が `nullptr` にされるので、トリガ内の文は独立したダイジェストにならない
- **`COM_RESET_CONNECTION` はセッション変数をグローバル値で丸ごと上書きする。** `THD::init` → `plugin_thdvar_init` の `thd->variables = global_system_variables`。1 変数ずつ既定に戻すのではないので、接続確立時に `SET` した値も消える
- **`THD::cleanup_connection` の `#ifndef NDEBUG` ブロックが、セッションの残留物の完全な一覧になっている** (分離レベル / autocommit / prepared_stmt_count / 診断エリア / 一時テーブル / `LOCK TABLES`)

| 95    | `undo-tablespaces-and-truncate`      | 背景スレッド    | 最小 2 個の理由、mark → empty → truncate の 3 段、round-robin 選択、truncate で space_id が変わる                                             |
| 98    | `dict-cache`                         | 背景スレッド    | `table_LRU` / `table_non_LRU`、外部キーと AHI は evict 不可、上限は `table_definition_cache`、active 50% / idle 100%                          |

既存ページの order は 群 8 以降を振り直した (56-58 据置、59-61 は -1 相当の再配置、以降は新規スロットを空けて +1〜+12)。DDL 以降は 100-124 のまま。

#### 計画から落としたページと理由

- **`page-search-and-directory` (ページ内探索とページディレクトリ)** — `page-layout` が `page_cur_search_with_match`、スロットの 4〜8 件所有、`PAGE_GARBAGE` まで既に書いており重複。代わりに `row-read-path` を群 10 に入れた
- **`buffer-pool-instances-and-resize`** — `buffer-pool-walkthrough` が chunk / instance / `buf_resize_thread` / dump-load を既にカバー。代わりに `innodb-memory` を置いた
- **`redo-format-and-resize`** — ログブロック 512B の構造は `redo-log-walkthrough`、`MLOG_*` は `mini-transaction`、`Log_files_capacity` と `innodb_redo_log_capacity` は `redo-log-walkthrough` にある。代わりに `redo-disabled-paths` を置いた

#### 増補で分かったこと

- **`row0del.cc` は存在しない。** DELETE は `ha_innobase::delete_row` が `upd_node->is_delete = true` を立てて `row_update_for_mysql` を呼ぶ。undo 側の `row0uins.cc` / `row0umod.cc` は別
- **7 分岐の割り当て関数は `fseg_alloc_page_no` (L2743)。** `fseg_alloc_free_page_low` (L2970) はそれを呼んで block を返すラッパ
- **`Data_free` はセグメント内の空きを数えない。** `fsp_get_available_space_in_free_extents` はフリーリスト + free limit 上の未初期化領域 − (2 エクステント + 1%)。1MB 未満のファイルは常に 0
- **`FLUSH TABLES ... FOR EXPORT` は `trx_purge_stop()` を呼ぶ。** 対象テーブルだけでなくサーバ全体の purge が止まる
- **セッション一時表領域が返却・truncate されるのは接続が切れたときだけ。** `DROP TEMPORARY TABLE` では戻らない (`Tablespace_pool::free_ts`)
- **`ibtmp1` にはもうユーザ一時表のデータは入らない。** 入るのは一時表用 rseg (`trx_sys->tmp_rsegs`)
- **`INNODB_SESSION_TEMP_TABLESPACES.ID` は space_id ではなくスレッド ID。** space_id は `SPACE` 列。`PURPOSE` に USER / INTRINSIC / SLAVE / NONE
- **`innodb_log_buffer_size` の既定は 8.4 で 64MB** (`INNODB_LOG_BUFFER_SIZE_DEFAULT`)。8.0 系の 16MB のつもりでメモリ見積もりをすると外す
- **`innodb_ddl_buffer_size` / `innodb_ddl_threads` は `MYSQL_THDVAR`** = セッション変数。同時 DDL 数と掛け算になる
- **Semaphore wait のクラッシュは 600 秒ちょうどではない。** 同じ待ち手・同じセマフォが 11 回連続 (約 11 秒) 観測されて初めて `ib::fatal`
- **先読み (fetch cache) は 5 行目から。** `n_rows_fetched >= MYSQL_FETCH_CACHE_THRESHOLD (4)` か `ROW_SEL_EXACT` のときだけ。`select_lock_type != LOCK_NONE` / BLOB / 主キーなしで無効
- **AHI の探索近道は 8.4 既定では使われない。** 条件に `btr_search_enabled` が入っており、`innodb_adaptive_hash_index` の既定が OFF
- **`ROLLBACK TO SAVEPOINT` はロックを 1 つも解放しない。** `trx_rollback_finish` を呼ぶのは `savept == nullptr` の完全ロールバックだけ
- **undo テーブルスペースの truncate は space_id を変える。** `trx_undo_truncate_tablespace` のコメントに明記。だから最小 2 個が要る
- **辞書キャッシュの上限は `table_definition_cache` を流用している。** `innobase_get_table_cache_size()` が `table_def_size` を返すだけで、InnoDB 専用の設定はない
