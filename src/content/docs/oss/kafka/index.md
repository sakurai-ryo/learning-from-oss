Apache Kafka は、**追記専用のログファイルを配るためのサーバ**だ。

送り手 (プロデューサ) はレコードをファイルの末尾に足す。受け手 (コンシューマ) は「自分は何バイト目まで読んだか」を覚えていて、そこから先を読む。読んでもレコードは消えない。これだけであれば、ただのファイルサーバである。

面白いのはその先だ。Kafka はこの「ログ」という 1 つの道具だけで、レプリケーション・クラスタ構成の管理・コンシューマの進捗管理・トランザクション・そしてキューまでを実装している。**ログの上に載せられるものは、全部ログの上に載せる** — この方針がコードのあらゆる階層に現れる。

**「追記専用ファイルという最小の道具で、分散システムをどこまで作れるか」** — この章はそれを追う。

## この OSS について

- Apache License 2.0。本体 (テストを除く) は Java 3,817 ファイル・約 68 万行、Scala 77 ファイル・約 3 万行。**テストコードは約 96 万行あり、本体より多い。**
- **Scala で書かれ始めたプロジェクトが、Java へ移り終わりかけている。** 残った Scala 77 ファイルの内訳は `KafkaApis` (4,404 行)、`ReplicaManager`、`Partition`、`SocketServer` — つまり最後まで残っているのは一番熱いところだ。新しいモジュール (`raft/`、`metadata/`、`group-coordinator/`、`storage/`) はすべて Java で書かれている。
- **4.0 で ZooKeeper が完全に消えた。** 代わりに Kafka 自身の Raft 実装 (KRaft) が `__cluster_metadata` という内部トピックにクラスタのメタデータを書く。「メタデータストアを外部に持つ分散システム」から「自分のログでメタデータを管理する分散システム」への転換であり、この章の 7 ページを占める。
- **ネットワークプロトコルはコードではなく JSON で定義される。** 265 個のスキーマファイルから Java クラスが生成される。各フィールドに「どのバージョンから存在するか」が書かれていて、後方互換性はコードレビューではなくスキーマの制約として守られている。
- **KIP (Kafka Improvement Proposal) 番号がコード中に 89 種類埋まっている。** 挙動の理由がコメントではなく KIP 番号で示されるので、`grep KIP-` が設計意図への索引として機能する。
- **ディスクとページキャッシュを信じ切っている。** ブローカーはレコードを JVM ヒープに載せずに、ファイルからソケットへ直接転送する。「速い分散システムを作るために、まず OS がすでに持っているものを使う」という判断が、コードの形を決めている。
- **後から入った大きな機能が、既存の構造をどう再利用したかが読みどころ。** 階層型ストレージ (古いセグメントをオブジェクトストレージへ)、共有グループ (ログの上にキューを載せる)、新しいリバランスプロトコル — いずれも既存のログとコーディネータの仕組みを土台にしている。
