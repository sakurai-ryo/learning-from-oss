## なぜこれを先に知る必要があるか

HTTP/1.1 のパーサは、Web サーバのソースの中でいちばん退屈で、いちばん長い部分だ。Nginx でいえば `ngx_http_parse.c` がそれにあたる。巨大な `switch` 文と大量の `state` 定数が並んでいて、一見すると何をやっているか分からない。

**なぜあの形になるのかは、HTTP/1.1 という書式が何を要求しているかを知らないと読めない。** そして要求の大半は「書式が複雑だから」ではなく、「バイトがいつどれだけ届くか分からないから」から来ている。

ここでは RFC 9112 (HTTP/1.1 のメッセージ構文) と RFC 9110 (HTTP のセマンティクス) を土台に、実際のバイト列を見る。文法そのものより、**その文法をパースする側が引き受ける面倒**を見つけるのが目的になる。

## メッセージの形

RFC 9112 §2.1 の ABNF がこれになる。

```
HTTP-message   = start-line CRLF
                 *( field-line CRLF )
                 CRLF
                 [ message-body ]

start-line     = request-line / status-line
request-line   = method SP request-target SP HTTP-version
status-line    = HTTP-version SP status-code SP [ reason-phrase ]
```

CRLF は `\r\n` の 2 バイト。SP は空白 1 個。実際のバイト列で書くと、リクエストはこうなる。

```
47 45 54 20 2f 69 6e 64 65 78 2e 68 74 6d 6c 20   G E T _ / i n d e x . h t m l _
48 54 54 50 2f 31 2e 31 0d 0a                     H T T P / 1 . 1 CR LF
48 6f 73 74 3a 20 65 78 61 6d 70 6c 65 2e 63 6f   H o s t : _ e x a m p l e . c o
6d 0d 0a                                          m CR LF
55 73 65 72 2d 41 67 65 6e 74 3a 20 63 75 72 6c   U s e r - A g e n t : _ c u r l
2f 38 2e 34 2e 30 0d 0a                           / 8 . 4 . 0 CR LF
0d 0a                                             CR LF   ← 空行 = ヘッダ終わり
```

読める形で書き直すと (`␍␊` が CRLF):

```
GET /index.html HTTP/1.1␍␊
Host: example.com␍␊
User-Agent: curl/8.4.0␍␊
␍␊
```

構造は 4 つ。**開始行、ヘッダの列、空行、ボディ。** 空行までがメタデータで、それ以降が本文。

### リクエストライン

`method SP request-target SP HTTP-version`。3 つのトークンが空白 1 個ずつで区切られる。

`method` は大文字小文字を区別する。`get` は `GET` ではない。RFC 9110 §9 に定義されているのは `GET` `HEAD` `POST` `PUT` `DELETE` `CONNECT` `OPTIONS` `TRACE` の 8 つだが、**サーバはこれ以外のメソッドを受け取ってもよい**。`PATCH` (RFC 5789) や WebDAV の `PROPFIND` は別の RFC で定義されている。

`request-target` には 4 つの形がある (RFC 9112 §3.2)。

| 形             | 例                              | 使う場面               |
| -------------- | ------------------------------- | ---------------------- |
| origin-form    | `/index.html?q=1`               | 通常のリクエスト       |
| absolute-form  | `http://example.com/index.html` | プロキシへのリクエスト |
| authority-form | `example.com:443`               | `CONNECT` のみ         |
| asterisk-form  | `*`                             | `OPTIONS *` のみ       |

サーバは 4 つ全部を受け付ける必要がある。absolute-form は「プロキシ用」だが、**RFC 9112 §3.2.2 はサーバに対しても受け入れを要求している。** リバースプロキシとして動くとき、絶対 URI の中のホストと `Host` ヘッダのどちらを見るかが問題になり、規格は絶対 URI を優先すると定めている。

`HTTP-version` は `HTTP/` に続けて `DIGIT "." DIGIT` の 3 バイト。`HTTP/1.1` は 8 バイト固定。

### ヘッダフィールド

RFC 9112 §5 の定義がこれ。

```
field-line   = field-name ":" OWS field-value OWS
field-name   = token
field-value  = *field-content
OWS          = *( SP / HTAB )
token        = 1*tchar
tchar        = "!" / "#" / "$" / "%" / "&" / "'" / "*"
             / "+" / "-" / "." / "^" / "_" / "`" / "|" / "~"
             / DIGIT / ALPHA
```

読み取れることが 4 つある。

**1. 名前とコロンのあいだに空白を入れてはいけない。** `OWS` はコロンの後ろにしかない。`Host : example.com` は不正で、RFC 9112 §5.1 は **サーバに 400 での拒否を要求している** (プロキシは前方に転送する前に削除しなければならない)。これは規格の細かい話ではなく、後述する request smuggling の入口を塞ぐための規定だ。

**2. 値の前後の空白は値に含まれない。** `Host:example.com` と `Host:   example.com   ` は同じ値を表す。パーサは値の開始位置と終了位置を、空白を飛ばして決める必要がある。

**3. 名前に使える文字が限定されている。** `tchar` に空白も制御文字もコロンも含まれない。ここを緩く受け入れると、`Transfer-Encoding\r\n : chunked` のような細工を通してしまう。

**4. 名前は大文字小文字を区別しない。** `Content-Length`、`content-length`、`CONTENT-LENGTH` は同じヘッダ。だから比較のたびに大文字小文字を無視した比較が要る。サーバがヘッダ名のハッシュを事前計算しておくのは、この比較を毎回やらないためだ。

行の折り返し (obs-fold) — 次の行を空白で始めて値の続きとする記法 — は、RFC 9112 §5.2 で **非推奨とされ、メッセージボディ内以外での受信は 400 で拒否するか、単一の SP に置き換えることが求められている。** これも smuggling 対策として厳格化された部分になる。

### 空行

`CRLF` が単独で 1 行。ここでヘッダが終わり、ボディが始まる。

**ヘッダが何個あるか、全体で何バイトになるかは、この空行が来るまで分からない。** サーバは空行を見つけるまで読み続けるしかない。上限を置かなければ、クライアントは無限にヘッダを送り続けられる。

## 「どこまでがボディか」を決める 2 通り

TCP は 1 本のバイトストリームで、メッセージの区切りを持たない。だから **HTTP は自分で終端を宣言しなければならない。** 手段は 2 つしかない。

### Content-Length

10 進数でバイト数を書く。

```
POST /submit HTTP/1.1␍␊
Host: example.com␍␊
Content-Type: application/x-www-form-urlencoded␍␊
Content-Length: 15␍␊
␍␊
q=nginx&lang=ja
```

空行の直後から数えて 15 バイトが本文になる。`q=nginx&lang=ja` がちょうど 15 バイトで、**その後ろに CRLF は付かない**。ボディはテキストではなくバイト列なので、行という単位を持たない。ここを CRLF 付きで数えると 2 バイトずれ、keep-alive で次のリクエストの先頭が壊れる。

単純だが、条件がある。**送り始める前に長さが分かっていないと使えない。** 動的に生成する応答や、上流から受け取りながら流すプロキシでは、長さが分からない。

### Transfer-Encoding: chunked

長さを先に言えないときの答え。**本文を塊 (chunk) に分けて、各塊の先頭にその塊の長さを書く。**

```
HTTP/1.1 200 OK␍␊
Content-Type: text/plain␍␊
Transfer-Encoding: chunked␍␊
␍␊
1a␍␊
abcdefghijklmnopqrstuvwxyz␍␊
5␍␊
01234␍␊
0␍␊
␍␊
```

`1a` は 16 進で 26。次の 26 バイトが本文の一部。`5` なら 5 バイト。`0` の塊が来たら終わり。

ABNF は RFC 9112 §7.1 にある。

```
chunked-body    = *chunk
                  last-chunk
                  trailer-section
                  CRLF

chunk           = chunk-size [ chunk-ext ] CRLF
                  chunk-data CRLF
chunk-size      = 1*HEXDIG
last-chunk      = 1*("0") [ chunk-ext ] CRLF

chunk-ext       = *( BWS ";" BWS chunk-ext-name
                     [ BWS "=" BWS chunk-ext-val ] )

trailer-section = *( field-line CRLF )
```

注意点が 4 つ。

- **サイズは 16 進**で、大文字小文字どちらでもよい。`1A` も `1a` も 26。先頭のゼロ埋めも許される。
- **`chunk-ext`** — サイズの後ろにセミコロン区切りの拡張を書ける。使われることはほぼ無いが、パーサはこれを読み飛ばせなければならない。ここを見落とすと、`5;foo=bar` を長さとして解釈しようとして壊れる。
- **末尾の 0 チャンクの後に trailer が来られる。** ボディを全部送り終えてから初めて分かる値 — チェックサムや処理時間 — をヘッダとして送るための仕組み。`Trailer` ヘッダで予告する。
- **`chunked` は transfer-coding の最後になければならない** (RFC 9112 §6.1)。`Transfer-Encoding: gzip, chunked` は正しいが、`chunked, gzip` は不正。リクエストでこの並びが不正なら、サーバは 400 を返して接続を閉じることが求められる。

chunked の利点は長さを先に言わなくていいことだが、**代償はバイト数が増えること**だ。各チャンクにサイズの行と CRLF が付く。小さいチャンクを大量に送ると、オーバーヘッドが本文に対して無視できなくなる。だからプロキシは、上流から来た細切れの応答をそのままチャンクにせず、ある程度まとめてから 1 チャンクにする。

### 終端が示されない場合

どちらのヘッダも無いとどうなるか。

- **リクエストの場合** — ボディは無いものとして扱う。だから `GET` に `Content-Length` を付けなければ、ボディは 0 バイト。
- **応答の場合** — **接続を閉じるまでが本文になる** (RFC 9112 §6.3)。HTTP/1.0 のサーバはこれをよく使った。

3 番目の「接続を閉じるまで」という終端の表し方には、致命的な欠点がある。**転送が完了したのか、途中で切れたのかを区別できない。** クライアントは全部受け取ったつもりで、実は途中までかもしれない。keep-alive とも両立しない。だから HTTP/1.1 では、この形はできるだけ避けられる。

### 両方あったら — request smuggling の温床

`Content-Length` と `Transfer-Encoding` が両方あったらどうするか。RFC 9112 §6.1 は明確に定めている。

> If a message is received with both a Transfer-Encoding and a Content-Length header field, the Transfer-Encoding overrides the Content-Length.

**chunked が勝つ。** そして続けて、これが request smuggling や response splitting の試みかもしれないと警告し、送信側は両方を送ってはならず、中継する場合は `Content-Length` を削除しなければならないと定めている。

なぜ危険か。**サーバが 2 台直列に並んでいて、2 台が違う解釈をすると、1 本のバイト列が「2 台で違う本数のリクエスト」に見える。**

```
POST / HTTP/1.1␍␊
Host: example.com␍␊
Content-Length: 47␍␊
Transfer-Encoding: chunked␍␊
␍␊
0␍␊
␍␊
GET /admin HTTP/1.1␍␊
Host: example.com␍␊
␍␊
```

空行より後ろは 47 バイトある。`0␍␊␍␊` の 5 バイトと、`GET /admin ...␍␊␍␊` の 42 バイト。

**前段のプロキシが `Content-Length: 47` に従えば**、47 バイト全部が 1 本のリクエストの本文だ。1 本のリクエストとして後段に転送する。

**後段のサーバが `Transfer-Encoding: chunked` に従えば**、本文は `0` チャンクで終わっているので 5 バイトで打ち切る。残った 42 バイトは、**次のリクエストの先頭**として読まれる。1 本送ったつもりが、後段では 2 本になっている。

そして 2 本目には、前段が付けたはずのもの — 認証済みユーザの識別、`X-Forwarded-For`、レート制限のカウント — が何も付いていない。前段の検査を素通りしたリクエストが、後段に直接届く。

これが CL.TE 攻撃。逆向き (前段が TE、後段が CL) の TE.CL もある。狙われるのは規格の解釈違いだけではない。

- `Transfer-Encoding: chunked ` (末尾に空白)
- `Transfer-Encoding: xchunked`
- `Transfer-Encoding:␍␊ chunked` (obs-fold)
- `Transfer-Encoding` を 2 回送る
- `Content-Length` を 2 回、違う値で送る
- ヘッダ名とコロンのあいだに空白を入れる

**どれも「片方のサーバは不正として無視し、もう片方は受け入れる」ことを狙っている。** 前述した「コロンの前に空白があれば 400」「obs-fold は 400」といった規定が厳しく書かれているのは、この解釈差を潰すためだ。

サーバ実装者の立場からは、規則は 1 つに集約される。**曖昧なものを受け取ったら、解釈せずに 400 を返して接続を閉じる。** 寛容に受け入れることが、直列に並んだ他のサーバとの解釈差を作る。

## Host が必須になった理由

HTTP/1.0 のリクエストには `Host` が無かった。

```
GET /index.html HTTP/1.0␍␊
␍␊
```

これで足りたのは、**1 つの IP アドレスに 1 つのサイトしか無かった**からだ。どのサーバに繋いだかで、どのサイトかが決まる。

サイトが増えて IP アドレスが足りなくなると、これが破綻する。1 台のサーバで `a.example.com` と `b.example.com` を運用したい。TCP 接続からは宛先 IP しか分からないので、区別できない。

HTTP/1.1 の答えが `Host` ヘッダで、RFC 9112 §3.2 が **HTTP/1.1 のリクエストには必ず含めなければならない**と定めている。サーバ側の要求はさらに強い。

- `Host` が無い HTTP/1.1 リクエストには **400 を返さなければならない**
- `Host` が 2 つ以上あるリクエストにも **400 を返さなければならない**
- 値が不正なら **400 を返さなければならない**

「必ずある」ことが保証されるので、サーバは `Host` を見てから設定を選べる。**名前ベースのバーチャルホストが成立する根拠が、この 1 つのヘッダにある。**

ただし穴がある。**TLS では、`Host` を読む前に証明書を出さなければならない。** 暗号化されているのだから当然で、これが SNI (Server Name Indication) が必要になった理由になる。TLS のハンドシェイクの中でホスト名を平文で伝え、それで証明書を選ぶ。つまり **同じ「どのサイトか」の情報を、TLS と HTTP の 2 箇所で伝える**ことになる。2 つが食い違ったときにどうするかは、サーバが決めなければならない。[TLS 終端のページ](../tls-termination/) で扱う。

HTTP/2 と HTTP/3 では `Host` は `:authority` という擬似ヘッダに置き換えられた。役割は同じだ。

## 接続の再利用

### keep-alive

HTTP/1.0 では 1 リクエストごとに TCP 接続を張って閉じるのが既定だった。1 ページに画像が 20 個あれば、TCP 接続を 21 回張ることになる。3 ウェイハンドシェイクだけで往復が 21 回。

HTTP/1.1 は **既定を逆にした。** 接続は再利用され、閉じたい側が `Connection: close` を明示する (RFC 9112 §9.3)。

```
GET /a HTTP/1.1␍␊
Host: example.com␍␊
␍␊
```

```
HTTP/1.1 200 OK␍␊
Content-Length: 5␍␊
␍␊
hello
```

```
GET /b HTTP/1.1␍␊    ← 同じ接続の続き
Host: example.com␍␊
␍␊
```

**これが成立するのは、応答の終端が正確に示されているからだ。** `Content-Length: 5` の 5 が 1 バイトでもずれれば、次のリクエストの先頭がずれる。「どこまでがボディか」を正しく表すことと、接続を使い回せることは、同じ 1 つの性質の 2 つの側面になっている。

サーバ側では、接続を維持することは資源を持ち続けることでもある。次のリクエストが来ないまま何分も居座られると困るので、アイドルタイムアウトと、1 接続あたりのリクエスト数の上限を持つ。

### パイプライン — なぜ実質死んだか

HTTP/1.1 は、応答を待たずに次のリクエストを送ることも許した。

```
GET /a HTTP/1.1␍␊Host: x␍␊␍␊GET /b HTTP/1.1␍␊Host: x␍␊␍␊GET /c HTTP/1.1␍␊Host: x␍␊␍␊
```

3 本まとめて送る。理屈の上では往復が 1 回で済む。

死んだ理由は 1 つだ。**応答は要求と同じ順序で返さなければならない。**

TCP の 1 本のストリームには、応答を区別する識別子が無い。だから受け取った側は「1 本目の応答、2 本目の応答、3 本目の応答」と順番でしか対応付けられない。サーバが `/b` を先に用意できても、`/a` が終わるまで送れない。

`/a` の生成に 3 秒かかり、`/b` と `/c` が即座に返せるなら、3 本とも 3 秒待たされる。これが head-of-line blocking で、**パイプラインは「速くなることもあるが、遅くなることもある」機能になった。** どちらになるかはサーバ側の都合次第で、クライアントには予測できない。

さらに実務上の問題が重なった。パイプラインを正しく扱えない中間プロキシが存在し、リクエストを取りこぼしたり順序を崩したりする。壊れ方が「一部のリクエストが静かに失われる」なので、原因の特定が難しい。

結果として、主要なブラウザはパイプラインを既定で無効にした。**この失敗が HTTP/2 の設計を直接規定している。** ストリーム ID を導入して応答に識別子を付ければ、順不同で返せる。HTTP/2 の多重化は、パイプラインが解けなかった問題への答えとして読むのが正確だ。[HTTP/2 と HTTP/3 のページ](../http2-http3/) で続きを見る。

### Connection: close

接続を閉じたいときは、**閉じる前の最後の応答に** `Connection: close` を付ける。

```
HTTP/1.1 200 OK␍␊
Content-Length: 5␍␊
Connection: close␍␊
␍␊
hello
```

クライアント側も、これ以上送らないなら最後のリクエストに付ける。

`Connection` ヘッダにはもう 1 つ役割がある。**ホップごとのヘッダを列挙する**ことだ。`Connection: keep-alive, Upgrade` と書けば、`Keep-Alive` と `Upgrade` の 2 つが「この接続だけの話であって、転送してはいけない」と宣言される。プロキシはこれらを削除してから前方に送らなければならない。

`Connection` 自体、`Keep-Alive`、`Transfer-Encoding`、`Upgrade`、`Proxy-Authenticate` などがホップごとのヘッダで、**プロキシを書く側は、転送するヘッダとしないヘッダを区別する表を持つことになる。**

## 100-continue

大きなボディを送る前に、サーバがそれを受け取る気があるか確かめたい。認証に失敗するリクエストや、大きすぎるアップロードを、100MB 送りきってから 401 や 413 で断られるのは無駄だ。

RFC 9110 §10.1.1 の `Expect` ヘッダがこれを扱う。

```
PUT /upload HTTP/1.1␍␊
Host: example.com␍␊
Content-Length: 104857600␍␊
Expect: 100-continue␍␊
␍␊
                                 ← ここで止まって待つ
```

サーバは 2 通りの返し方をする。

```
HTTP/1.1 100 Continue␍␊
␍␊
```

→ クライアントはボディを送り始める。この後、処理が終わったら最終応答をもう 1 つ送る。**1 リクエストに対して応答が 2 つ流れる。**

```
HTTP/1.1 413 Content Too Large␍␊
Content-Length: 0␍␊
Connection: close␍␊
␍␊
```

→ ボディは送られない。

実装上の注意が 3 つある。

- **クライアントは無限には待たない。** 一定時間で諦めてボディを送り始める。だからサーバは、100 を返さなかったのにボディが来ることを想定しなければならない。
- **HTTP/1.0 のクライアントには 100 を送ってはいけない。** 1xx を理解しないので、応答として誤解される。
- **既にボディを受け取ってしまった後で 100 を送ってはいけない** (RFC 9110 §10.1.1)。意味がない。

1xx は「中間応答」で、最終応答の前に何個でも来られる。103 Early Hints も同じ枠組みだ。**クライアントのパーサは、応答を 1 つ読んだら終わり、という構造では書けない。**

## 応答側

### ステータス行

```
HTTP/1.1 404 Not Found␍␊
```

`status-code` は 3 桁の数字。`reason-phrase` は人間向けの文字列で、**省略してもよく、クライアントは無視することになっている** (RFC 9112 §4)。`HTTP/1.1 404 ␍␊` は正しい。

RFC 9110 §15 の分類は 5 つ。1xx が中間応答、2xx が成功、3xx がリダイレクト、4xx がクライアント側の誤り、5xx がサーバ側の誤り。**クライアントは知らないステータスコードを、その百の位の代表 (`599` なら `500`) として扱わなければならない。** だから新しいコードを足しても既存のクライアントが壊れない。

### ボディを持たない応答

これがパースの分岐を作る。次の場合、**`Content-Length` が付いていても本文は存在しない** (RFC 9112 §6.3)。

- **`HEAD` への応答** — ヘッダは `GET` と同じものを返す。つまり `Content-Length: 1234` と書いてあるのに、本文は 0 バイト。
- **204 No Content** — 本文を持たない。
- **304 Not Modified** — 本文を持たない。`Content-Length` を付けてもよいが、本文は続かない。
- **1xx** — すべて本文を持たない。
- **`CONNECT` への 2xx** — 以降は本文ではなく、トンネルされたバイト列になる。

**ここを間違えると接続の同期が壊れる。** `HEAD` の応答の後に 1234 バイト読もうとすれば、次の応答の先頭を本文として食ってしまう。

サーバ側でも同じ注意が要る。204 を返すコードパスが誤って本文を書けば、クライアントはそれを次の応答のステータス行として読む。**`Content-Length` の値と、実際に書いたバイト数と、本文を持つべきかどうか — この 3 つを一致させ続けるのが、応答生成側の主な責務になる。**

## サーバ実装者にとって何が面倒か

文法をここまで見てきたが、パーサが複雑になる原因は文法そのものではない。

### 1. 行がいつ届くか分からない

TCP はバイトストリームで、メッセージの境界を保存しない。`GET /index.html HTTP/1.1␍␊` の 26 バイトが 1 回の `read()` で来る保証はどこにもない。

```
read() 1 回目 → "GE"
read() 2 回目 → "T /ind"
                    (300ms 経過)
read() 3 回目 → "ex.html HTTP/1.1␍␊Host: exa"
read() 4 回目 → "mple.com␍␊␍␊"
```

**1 バイトずつ届いても正しく動く必要がある。** これは仮定の話ではなく、Nagle アルゴリズムと遅延 ACK の組み合わせ、MTU による分割、そして意図的な攻撃 (Slowloris) で日常的に起きる。

この要求が、パーサの形をほぼ決めてしまう。

- **「1 行読む」という関数が書けない。** 行が揃っている保証がないので、途中で止まって、次のデータが来てから続きをやる形にするしかない。
- **状態を明示的に持つしかない。** 「メソッドを読んでいる途中」「ヘッダ名を読んでいる途中」「CR は見たが LF はまだ」といった位置を、変数として保存する。関数のローカル変数やコールスタックには置けない。中断して戻ってくるからだ。
- **バッファをまたぐ。** `Content-Length` という 14 バイトの名前が、2 回の `read()` に分かれて届くかもしれない。文字列比較で判定するなら、バイトを 1 箇所に集めるコピーが要る。1 バイトずつ状態遷移するなら、コピーは要らないが状態の数が増える。

結果として、HTTP パーサは **大きな `switch` 文と大量の状態定数**という形に収束する。読みにくいのは書き方が悪いからではなく、要求がそういう形を強制しているからだ。

もう 1 つの帰結として、**パースの途中経過を保持するメモリが、接続ごとに要る。** 5 万接続あれば 5 万個ぶんのパース状態が同時に生きる。この構造体を小さくすることが、そのまま同時接続数の上限になる。

### 2. 上限を自分で決める必要がある

RFC 9112 は、ヘッダの個数にも長さにも上限を定めていない。定めていないので、**上限を置くかどうかはサーバの判断になる。**

置かなければ何が起きるか。

- ヘッダを 100 万個送りつけられる
- 1 行を 1GB にされる
- リクエストラインの URI を無限に長くされる

どれもメモリを食い尽くす。だから全ての実装が独自の上限を持つ。RFC 9110 §15.5.15 の 431 Request Header Fields Too Large は、そのために用意されたステータスコードだ (RFC 6585 で導入され、RFC 9110 に統合された)。

上限を置くと、今度は別の問題が出る。**どこで上限を判定するか。** 1 行の長さの上限は、その行を読み切る前に判定できる — バッファが埋まった時点で打ち切ればいい。ヘッダ全体のサイズの上限も、累積で数えれば途中で分かる。ところが「ヘッダの個数」は、数え方を決めないと判定できない。

そして上限の値そのものが、運用上の制約になる。Cookie が大きいサイト、JWT を `Authorization` に入れるサイト、長いクエリ文字列を使う API。**上限を上げると攻撃耐性が下がり、下げると正当なリクエストが 400 や 431 で弾かれる。** 「4KB のバッファをいくつまで使ってよいか」という形でこれを表現するのが、Nginx のやり方になる。

### 3. 寛容さが脆弱性になる

Postel の法則 — 送るものには厳格に、受け取るものには寛容に — は、HTTP に関しては危険な助言だと分かった。理由は前述のとおりで、**サーバが直列に並ぶから**だ。

1 台なら、寛容であることの害は小さい。おかしなリクエストを善意に解釈して処理するだけだ。ところが 2 台並ぶと、「A は受け入れて B は拒否する」入力の存在そのものが攻撃面になる。

RFC 9112 が「〜しなければならない (MUST)」で拒否を要求している箇所が多いのは、この認識の結果だ。パーサを書く側の指針も 1 つに絞られる。

**規格に無い形を受け取ったら、直して受け入れるのではなく、400 を返して接続を閉じる。** 接続を閉じるところまでが重要で、閉じずに次のリクエストを読もうとすると、バッファに残ったバイトの解釈が攻撃者の手に落ちる。

### 4. 応答を組み立てる側にも同じ制約がある

パースの裏返しとして、書き出す側も 1 回で書ける保証がない。`write()` が「3 バイトだけ書けた」と返すことがある。だから応答の生成も、**どこまで書いたかを状態として持って、中断・再開できる形**でなければならない。

さらに、パースと違って生成側には順序の制約がある。ヘッダを送り出してしまった後では、`Content-Length` を変更できない。**ボディの加工 (gzip など) をするなら、ヘッダを送る前に「長さが変わる」ことを決めておかなければならない。** 圧縮後のサイズは圧縮してみないと分からないので、実際には `Content-Length` を捨てて chunked に切り替えることになる。

つまり **「どこまでがボディか」の 2 通りの表現は、応答を加工する仕組み全体の設計に効いてくる。** 何をどの順で決めるかという依存関係が、出力側の構造を規定する。
