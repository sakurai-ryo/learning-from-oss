Nginx は HTTP サーバであり、リバースプロキシであり、TCP/UDP のロードバランサでもある。ワーカープロセスは CPU コア数ぶんしか立たず、各ワーカーは 1 スレッドで動く。そのたった 1 つのスレッドが数万の接続を持ち、`epoll` から返ってきたイベントを順に処理していく。

この章は 2 つのことをやる。**Web サーバというプログラムが結局のところ何をしているのか**を、TCP のソケットから HTTP/3 まで前提から積み上げること。そして **Nginx がそれをどう実装しているか**を、`main()` から接続の終了まで通しで読むことだ。

## この OSS について

- Igor Sysoev が 2002 年に書き始め、2004 年に公開。現在は F5 傘下の Nginx, Inc. が開発している。2-clause BSD。
- `src/` は 25 万行の C。内訳は次のとおり (`release-1.31.4` で実測)。

  | ディレクトリ            | ファイル数 |   行数 | 中身                                                        |
  | ----------------------- | ---------: | -----: | ----------------------------------------------------------- |
  | `core/`                 |         82 | 33,642 | プール・バッファ・文字列・赤黒木・ハッシュ・設定パーサ・DNS |
  | `event/`                |         19 | 16,923 | イベントループ・接続・OpenSSL の統合                        |
  | `event/modules/`        |         10 |  5,087 | epoll / kqueue / poll / select / eventport / IOCP           |
  | `event/quic/`           |         30 | 16,759 | QUIC トランスポート                                         |
  | `http/`                 |         26 | 40,518 | HTTP のコア。リクエスト処理・upstream・変数・キャッシュ     |
  | `http/modules/`         |         62 | 69,293 | proxy / fastcgi / gzip / ssi / rewrite など                 |
  | `http/v2/`              |          7 |  8,247 | HTTP/2                                                      |
  | `http/v3/`              |         13 |  7,359 | HTTP/3                                                      |
  | `stream/`               |         33 | 24,923 | L4 プロキシ                                                 |
  | `mail/`                 |         19 | 10,795 | IMAP / POP3 / SMTP プロキシ (この章では扱わない)            |
  | `os/unix/`, `os/win32/` |         99 | 16,838 | プラットフォーム差の吸収                                    |

  外部依存は OpenSSL・zlib・PCRE だけ。コンテナ実装からフォーマット文字列まで自前で持っている。

- 読みどころは、**「1 スレッドを絶対にブロックさせない」という 1 つの制約が、コードのあらゆる階層の形を決めている** ところ。関数はいつでも `NGX_AGAIN` を返して途中で帰れなければならず、だから処理はコールバックの付け替えによるステートマシンになる。ローカルなスタック変数に状態を置けないので、状態はリクエスト構造体のビットフィールドに集まる。`read()` が返ってこない可能性のある操作 (ディスク I/O、DNS、上流への接続) は、すべて自前で非同期化してある。
- もう 1 つは、**メモリの解放を個別に書かない** こと。ほぼすべての確保はリクエストやコネクションに紐づいたプールから取られ、リクエストが終わるときに丸ごと返る。この方針が、エラーパスから `free()` を消し、`goto cleanup` の連鎖を消している。
- そして、20 年以上ほとんど変わっていない骨格の上に、HTTP/2 と HTTP/3 (QUIC) が後から載っていること。多重化もストリームも想定していなかったはずの「1 コネクション 1 リクエスト」のコードに、ほぼ手を入れずに済ませた層の作り方は、それ自体が読む価値のある設計判断になっている。

## 読む順番

3 つの系統が並んでいる。

**前提の 9 ページ**は、Nginx のコードをまだ開かない。ソケットと HTTP と多重化 API と TLS の話をする。「Web サーバを自分で書くとしたら何を決めなければならないか」を先に一通り並べておくと、Nginx のコードが「その決定の 1 つの回答」として読める。ここを飛ばすと、後半で出てくる型が何のための型なのか分からなくなる。

**骨格の 23 ページ**は、Nginx を縦に貫く通し解説だ。`main()` が何を組み立て、`accept()` の戻り値がどの構造体になり、バイト列がどこでリクエストに変わり、どの順で加工されて送り返されるか。順番に読むと、コードを開いたときに自分がどこにいるか分かるようになる。

**掘り下げの 12 ページ**は、骨格の 1 点を深く掘ったものだ。「なぜプールなのか」「なぜ赤黒木なのか」「なぜ DNS クライアントを自分で書いたのか」といった設計判断を扱う。骨格側の各ページから該当箇所へリンクしてある。

Nginx のコードを読んだことがなければ、[全体像のページ](./architecture/) を先に見てほしい。前提群で導入した語彙と Nginx の型名の対応表がそこにある。
