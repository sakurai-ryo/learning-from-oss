## 仮想化の出発点：トラップ&エミュレート

[前のページ](../why-microvm/)で、VM の分離境界はハードウェアにあると書いた。では、ハードウェアは具体的に何をしているのか。

仮想化の古典的な原理は、1974 年の Popek と Goldberg の定式化にさかのぼる。考え方はこうだ。

ゲスト OS のコードのうち、大半は「ふつうの命令」だ。`add`、`mov`、`jmp`、メモリの読み書き。これらは実 CPU 上でそのまま実行して問題ない。むしろそうしないと速度が出ない。

問題は残りの一部、**特権命令**だ。ページテーブルのベースアドレスを書き換える、割り込みを禁止する、I/O ポートに書き込む。これらをゲストにそのまま実行させると、ホストや他のゲストの状態を壊す。

そこで、こうする。

```
ゲスト OS を非特権モード (ring 3 相当) で走らせる
   |
   +-- ふつうの命令 --> そのまま実行 (高速)
   |
   +-- 特権命令      --> CPU が例外を上げる (トラップ)
                            |
                            v
                     VMM が制御を受け取る
                            |
                            v
                     「ゲストがやりたかったこと」を
                     VMM の側で安全に模倣する (エミュレート)
                            |
                            v
                     ゲストに制御を返す
```

これが **トラップ&エミュレート** だ。特権命令だけを VMM が肩代わりし、それ以外は実 CPU に任せる。

Popek と Goldberg は、この方式が成立する条件を示した。ざっくり言えば「**センシティブな命令（マシンの状態を読んだり変えたりする命令）が、すべて特権命令の部分集合である**」ことだ。センシティブなのに非特権のまま実行できてしまう命令が 1 つでもあれば、VMM はそれを捕まえられない。

## x86 が素朴にはできなかった理由

x86 は、長らくこの条件を満たしていなかった。センシティブなのに、非特権モードで実行しても**例外を上げずに黙って別の結果を返す**命令が存在したからだ。

代表例が `POPF` だ。スタックからフラグレジスタ（EFLAGS）を復元する命令で、EFLAGS には割り込み許可フラグ（IF）が含まれる。ゲスト OS が「割り込みを禁止する」つもりで `POPF` を実行しても、非特権モードでは IF の書き換えだけが**無視される**。例外は上がらない。命令は成功したように見えて、IF は変わっていない。

VMM から見ると、これは最悪の挙動だ。トラップが起きないのだから、「ゲストが割り込みを禁止しようとした」ことを知りようがない。ゲスト OS は割り込みを止めたつもりでクリティカルセクションに入り、そこに割り込みが飛んできて壊れる。同様の問題を起こす命令は x86 に 17 個ほどある（`SGDT`、`SIDT`、`SLDT`、`SMSW` など、記述子テーブルレジスタを非特権で読めてしまうものを含む）。

この時代の VMM は力技で回避していた。**バイナリ変換**（ゲストのコードを実行前にスキャンし、問題のある命令を安全な呼び出しに書き換える。VMware の初期実装）と、**準仮想化**（ゲスト OS のソースを改変し、特権命令を VMM へのハイパーコールに置き換える。Xen の初期実装）だ。どちらも動くが代償が大きい。前者は実装が複雑で変換のオーバーヘッドがあり、後者は改変されていない OS を動かせない。

## VT-x が追加したもの：もう 1 本の軸

Intel VT-x（AMD なら AMD-V / SVM）は、この問題を「新しい命令を特権化する」のではなく、**新しい直交する軸を追加する**ことで解決した。

従来、x86 の実行モードは ring 0〜3 という 1 本の軸だった。VT-x はこれに **VMX root / VMX non-root** という軸を足した。

```
                 VMX root モード          VMX non-root モード
              (ホスト = KVM がいる)      (ゲストがいる)
            +----------------------+  +----------------------+
   ring 0   |  ホストカーネル      |  |  ゲストカーネル      |
            |  (KVM)               |  |                      |
            +----------------------+  +----------------------+
   ring 3   |  ホストのユーザー    |  |  ゲストのユーザー    |
            |  プロセス            |  |  プロセス            |
            |  (Firecracker)       |  |                      |
            +----------------------+  +----------------------+
                       ^                         |
                       |      VM exit            |
                       +-------------------------+
                       |      VM entry           |
                       +------------------------>+
```

ポイントは、**ゲストカーネルが non-root の ring 0 で動く**ことだ。ゲスト OS は自分が ring 0 にいると認識している。だから改変が要らない。準仮想化のようにソースをいじる必要がない。

そのうえで、non-root モードでは「ホストに影響する操作」が VM exit を引き起こすように設定できる。`POPF` の IF 書き換えのような問題も、VT-x では割り込みウィンドウの制御としてハードウェアが面倒を見る。センシティブな命令はすべて捕まえられるようになった。

## VM entry と VM exit

この 2 つのモードを行き来する遷移に名前がついている。

- **VM entry**: root → non-root。VMM が「ゲストを走らせろ」と CPU に命じる。x86 の命令としては `VMLAUNCH` / `VMRESUME`。
- **VM exit**: non-root → root。ゲストが何かをやらかした（または外部要因が発生した）ので、CPU が自動的にホストに制御を戻す。

VM exit を起こす理由（exit reason）は多数ある。x86 では 60 個以上の exit reason が定義されている。主なものは以下。

| 種類           | 何が起きたか                                                |
| -------------- | ----------------------------------------------------------- |
| I/O 命令 (PIO) | ゲストが `in` / `out` 命令で I/O ポートにアクセスした       |
| EPT violation  | ゲストが未マップの物理アドレスにアクセスした（MMIO の実体） |
| CPUID          | ゲストが `cpuid` 命令を実行した                             |
| MSR read/write | ゲストが `rdmsr` / `wrmsr` を実行した                       |
| HLT            | ゲストが `hlt` 命令を実行した（やることがなくなった）       |
| 外部割り込み   | ホスト側の割り込みが入った（タイマー、シグナルなど）        |

VM exit は仮想化のコストの主要因だ。exit のたびに CPU はゲストの状態を保存し、ホストの状態を復元し、ホスト側のコードを実行し、また逆をやる。数百〜数千サイクルかかる。だから VMM の性能改善は、しばしば「VM exit を減らす」ことに帰着する。後で見る virtio の通知抑制（[notification-suppression](../notification-suppression/)）や ioeventfd の話は、まさにこの文脈にある。

## VMCS：ゲストの状態を入れる箱

モードを行き来するということは、レジスタの中身を丸ごと入れ替えるということだ。ゲストの RIP、RSP、CR3、セグメントレジスタ……。これを CPU が自動でやるために、VT-x は **VMCS (Virtual Machine Control Structure)** という 4KiB のメモリ領域を使う。AMD-V では VMCB と呼ぶ。

VMCS の中身は、大きく次の 4 つに分かれる。

```
+-------------------------------------------------------+
| VMCS (1 vCPU につき 1 つ、4KiB)                       |
+-------------------------------------------------------+
| Guest-state area    entry でここから CPU にロード     |
|                     exit  でここへ CPU から保存       |
|                     RIP, RSP, RFLAGS, CR0/3/4, seg... |
+-------------------------------------------------------+
| Host-state area     exit でここから CPU にロード       |
|                     → ホストカーネルの文脈に戻る      |
+-------------------------------------------------------+
| VM-execution control  「どの操作で exit するか」の設定 |
+-------------------------------------------------------+
| VM-exit information   なぜ exit したか + 付随情報      |
+-------------------------------------------------------+
```

VMCS の意味を一言でまとめるなら、**「ゲストのレジスタ状態を保存しておく箱」であり、同時に「どこで exit するかのポリシーを書いておく箱」**だ。VM entry は「箱からレジスタをロードして走り出す」、VM exit は「レジスタを箱にしまってホストの状態に戻る」。この保存・復元をハードウェアがやるので、ソフトウェアが 1 レジスタずつ退避する必要がない。

VMCS には直接 `mov` でアクセスできない。専用の `VMREAD` / `VMWRITE` 命令を使う。フィールドの物理レイアウトは CPU 実装依存で、ソフトウェアは「フィールド番号」で読み書きする。

## EPT：アドレス変換をもう 1 段ハードウェアでやる

もう 1 つ、VT-x 世代で追加された大きな仕組みが **EPT (Extended Page Table)** だ。AMD では NPT (Nested Page Table)、総称して「二段階アドレス変換」と呼ばれる。

問題はこうだ。ゲスト OS は自分のページテーブルで、ゲスト仮想アドレス (GVA) をゲスト物理アドレス (GPA) に変換する。ゲストは GPA を「本物の物理アドレス」だと思っているが、実際には GPA はホスト上のどこかのメモリでしかない。

EPT がない時代、VMM は「シャドウページテーブル」でこれを解決していた。ゲストのページテーブルを監視し、GVA → ホスト物理アドレス (HPA) を直接引く別のテーブルを VMM 側で維持する。ゲストがページテーブルを書き換えるたびに VM exit させて追随する必要があり、複雑で遅かった。EPT は、この 2 段目の変換をハードウェアに持たせた。

```
   ゲスト仮想アドレス (GVA)
            |
            |  ゲストのページテーブル (CR3 がゲストのものを指す)
            |  ゲスト OS が管理
            v
   ゲスト物理アドレス (GPA)
            |
            |  EPT (EPTP が指す)
            |  KVM が管理
            v
   ホスト物理アドレス (HPA)
```

MMU は 2 段のテーブルを両方引いて、GVA から HPA まで一気に変換する。ゲストが自分のページテーブルを書き換えても VM exit は起きない。ゲスト内のページフォルトはゲストカーネルが処理する。

VM exit が起きるのは、**EPT の側で変換に失敗したとき**だ。これを EPT violation という。「ゲストがアクセスした GPA が、EPT にマップされていない」あるいは「マップされているが権限が足りない」場合に発生する。

これがなぜ重要かというと、**MMIO の実現方法がまさにこれ**だからだ。ゲストが `0xd0000000` に書き込む。VMM はその GPA を EPT に一切マップしていない。だから EPT violation が起きて VM exit する。VMM は exit 情報から「どのアドレスに、何バイト、何を書こうとしたか」を読み取り、対応するデバイスモデルにその書き込みを渡す。ゲストから見れば、そこにデバイスのレジスタがあるように見える。

つまり、**「メモリマップド I/O」の正体は「わざと穴を開けておいたアドレス空間」** だ。この穴の話は[ゲスト物理メモリは、ホストプロセスの mmap にすぎない](../guest-memory/)でもう一度出てくる。

## この層は Firecracker には見えない

ここまで説明した VMCS、VM entry/exit の機構、EPT のページテーブル操作。これらは全部 **KVM（ホストカーネル内のモジュール）が担当する**。Firecracker のソースコードには `VMREAD` も `VMLAUNCH` も出てこないし、EPT のエントリを組み立てるコードもない。

Firecracker がやるのは、`/dev/kvm` に対する ioctl だけだ。「VM を作れ」「vCPU を作れ」「このメモリ範囲をゲスト物理アドレスのここに割り当てろ」「vCPU を走らせろ」。VMCS の組み立ても EPT の構築も、KVM の中で完結する。

Firecracker から見えるのは、**exit の結果だけ**だ。「vCPU を走らせろ」と頼んだら制御が戻ってきて、「MMIO のリード要求だった」「PIO のライト要求だった」という**分類済みの情報**が渡される。

その受け口が `handle_kvm_exit` だ。

```rust title="src/vmm/src/vstate/vcpu.rs"
/// Handle the return value of a call to [`VcpuFd::run`] and update our emulation accordingly
fn handle_kvm_exit(
    peripherals: &mut Peripherals,
    emulation_result: Result<VcpuExit, errno::Error>,
) -> Result<VcpuEmulation, VcpuError> {
    match emulation_result {
        Ok(run) => match run {
            VcpuExit::MmioRead(addr, data) => {
                data.fill(0);
                if let Some(mmio_bus) = &peripherals.mmio_bus {
                    let _metric = METRICS.vcpu.exit_mmio_read_agg.record_latency_metrics();
                    if let Err(err) = mmio_bus.read(addr, data) {
                        warn!("Invalid MMIO read @ {addr:#x}:{:#x}: {err}", data.len());
                    }
                    METRICS.vcpu.exit_mmio_read.inc();
                }
                Ok(VcpuEmulation::Handled)
            }
```

[`src/vmm/src/vstate/vcpu.rs#L435-L452`](https://github.com/firecracker-microvm/firecracker/blob/cc535f035f3828b2c5bfc85276c5d394022ed220/src/vmm/src/vstate/vcpu.rs#L435-L452)

`VcpuExit::MmioRead(addr, data)` に注目してほしい。前節で説明した EPT violation は、ここまで来ると「アドレス `addr` に対する読み出しで、結果を `data` に埋めてくれ」という要求に還元されている。VMCS のどのフィールドから exit reason を読んだか、EPT のどのレベルで変換に失敗したか、といった情報は KVM が吸収済みだ。Firecracker がやるのは、`mmio_bus` にアドレスを引かせて、担当するデバイスモデルに処理を委ねることだけになる。

x86 特有の PIO も同じ形で届く。こちらはアーキテクチャ固有の `run_arch_emulation` が `VcpuExit::IoIn` / `IoOut` を受け、`pio_bus` に流す（[`src/vmm/src/arch/x86_64/vcpu.rs#L757-L779`](https://github.com/firecracker-microvm/firecracker/blob/cc535f035f3828b2c5bfc85276c5d394022ed220/src/vmm/src/arch/x86_64/vcpu.rs#L757-L779)）。MMIO と PIO で扱いが分かれているのは、x86 に I/O ポートという別のアドレス空間が歴史的に存在するからだ。`in` / `out` 命令が使う 16 ビットの空間で、メモリとは完全に独立している。aarch64 には I/O ポートがないので、この関数はアーキテクチャ固有ファイルに置かれている。前ページで見たシリアルポート（`0x3f8`）と i8042（`0x060`）は、この PIO 空間にいるデバイスだ。

`METRICS.vcpu.exit_mmio_read` のようなカウンタが exit の種類ごとに置かれているのも示唆的で、VM exit の回数と種類が性能上の関心事であることを、コードそのものが表明している。
