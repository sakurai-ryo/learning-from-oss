## celld が解いている問題

チャットルームを 1 万部屋ホストしたいとする。部屋ごとに「今誰がいるか」「最新のメッセージは何か」という状態があり、それを壊さずに保ちたい。サーバーは 1 台では足りないので 10 台並べる。ここで問題が生まれる。**ある部屋の状態は、10 台のうちどの 1 台が担当するのか。そしてその 1 台が突然死んだら、誰がどうやって引き継ぐのか。**

celld では、この「部屋」にあたるものを**セル**と呼ぶ。セル 1 つは小さな SQLite データベース 1 つで、JavaScript のコード (Cloudflare の Durable Objects と同じ API) がそれを読み書きする。サーバー 1 台を**ノード**と呼ぶ。

普通の分散システムは、この「誰が担当か」を決めるために、ZooKeeper や etcd のような専用の調停サービスを別に立てる。celld はそれを持たない。代わりに **S3 のようなオブジェクトストレージ (バケット)** を、データの保管場所としてだけでなく、調停役としても使う。ノード同士は直接相談せず、全員が同じバケットを見て判断する。

## 所有権: セルを担当できるのは 1 台だけ

あるセルを担当する権利を**所有権**と呼ぶ。同じセルを 2 台が同時に担当すると、両方が別々に書き込んで状態が食い違う。この状態を**二重所有** (split-brain) と呼び、分散システムでもっとも避けたい事故の 1 つだ。

celld は、セルごとにバケットに 1 つの小さなファイル (**所有権レコード**) を置く。中身は「このセルの担当はノード A」という 1 行だ。担当したいノードはこのファイルを書き、書けた 1 台だけが担当になる。

## 条件付き書き込み: 「誰も書いていなければ書く」をストレージにやらせる

「書けた 1 台だけ」を実現するには、2 台が同時に書こうとしたとき片方だけが成功する仕組みが要る。S3 には、これを実現するオプションが 2 つある。

- 「このキーがまだ存在しないときだけ作成する」(`If-None-Match: *`)
- 「私が読んだときの版 (etag) から変わっていないときだけ上書きする」(`If-Match: <etag>`)

これを**条件付き書き込み**、あるいは compare-and-swap の頭文字で **CAS** と呼ぶ。ノード A と B が同時に「担当はわたし」と書こうとしても、ストレージは片方を受け付け、もう片方を「条件不成立」で拒否する。拒否された側は諦めて、受け付けられた側に処理を転送する。

celld はこの 2 つの操作だけを調停の土台にしている。だから、条件付き書き込みを正しく実装していないストレージ (MinIO のコミュニティ版など) では動かせない。[条件付き書き込みの検証](../conditional-write-contract/) は、その前提を信じずに確かめる話だ。

## エポック: 担当が変わるたびに増える番号

所有権レコードには、担当ノード名のほかに**エポック**という番号が入っている。担当が決まる (または変わる) たびに 1 増える。ノード A が 1 番、A が死んで B が引き継げば 2 番、という具合だ。

なぜ番号が要るのか。ノード A が「死んだ」と判断されて B に引き継がれたあと、実は A は死んでおらず、ネットワークが一瞬切れていただけだった、という状況を考える。A は自分が担当でなくなったことに気づかず、書き込みを続けるかもしれない。この「もう担当ではないのに動いている古いノード」を**古い所有者** (stale owner) と呼ぶ。

古い所有者の書き込みを無害にする仕掛け全般を**フェンシング** (fencing、柵で囲うこと) と呼ぶ。エポックはそのための道具で、celld は複製データの保存先パスにエポック番号を含める (`cells/部屋1/ltx/e2/...`)。古い所有者 A は `e1/` に書き続けるが、新しい担当 B は `e2/` に書き、復元のときは番号が大きい方だけを読む。A の書き込みは誰にも読まれない場所に落ちる。[エポックフェンス](../epoch-fence/) がこの話だ。

## リース: 「まだ生きている」を期限付きで宣言する

ノードが死んだかどうかは、外から見ても分からない。返事がないのは死んだからか、ネットワークが遅いだけか、区別できないからだ。分散システムはこれを**リース** (lease、期限付きの貸与) で扱う。

各ノードはバケットに「わたしは生きている。有効期限は 10 秒後」というファイルを書き、期限が来る前に書き直し続ける。他のノードは、期限が過ぎたファイルを見たら「このノードは死んだ」とみなして、そのノードが担当していたセルを引き継ぐ。

裏返すと、**リースを更新できなくなったノードは、自分から担当をやめなければならない**。まだ動いていても、他のノードはもう自分を死んだ扱いにしているからだ。これを self-fence (自分で自分に柵をする) と呼び、celld ではプロセスを終了することで実現する。[self-fence のページ](../self-fence/) が扱う。

## 曖昧なエラー: 「書けたかどうか分からない」がいちばん厄介

ネットワーク越しに書き込みを送って、返事が来なかったとする。送った書き込みは届いていない (書けていない) かもしれないし、届いたが返事だけが失われた (書けている) かもしれない。この状態を celld は**曖昧** (ambiguous) と呼び、「書けていない」と確定できるエラー (**確定** definite) と厳密に区別する。

なぜ区別が要るのか。条件付き書き込みが曖昧なとき、「失敗したのだろう」と決めつけてもう一度同じ書き込みを送ると、1 回目が実は成功していた場合に、自分の 1 回目とぶつかって拒否される。「拒否された = 他の誰かが担当になった」と誤解し、実際は自分が担当なのに処理を放棄する。曖昧なときはやみくもに再送せず、いったんファイルを読み直して現状を確かめるのが正しい。

## ack と耐久性: 「保存しました」と言って良いのはいつか

クライアントが書き込みを送り、サーバーが「保存しました」と返事することを **ack** (acknowledge) と呼ぶ。問題は、ack のあとでサーバーが死んだときにそのデータが残っているか、だ。

celld の各セルはノードのローカルディスク上の SQLite に書く。ローカルに書けただけで ack すると、ノードのディスクごと失われたときにデータが消える。だから celld は、書き込みがバケットに**複製**されたことを確認してから ack する。これを「ack したデータは 1 件も失わない」という意味で **RPO=0** (Recovery Point Objective がゼロ) と呼ぶ。

ただし ack のたびにバケットへの往復を待つと遅くなる。celld の答えは、書き込み自体はすぐ終わらせ、**クライアントへの返事だけを止めておく**ことで、これを**出力ゲート** (output gate) と呼ぶ。[出力ゲートのページ](../output-gate/) が扱う。

## テイクオーバーとリストア: 死んだノードのセルを引き継ぐ

ノード A が死んだ (リースが切れた) とき、A が担当していたセルへのリクエストが B に来たとする。B は、所有権レコードを条件付きで書き換えて担当になり (**テイクオーバー**)、バケットにある複製から SQLite を組み立て直す (**リストア**)。このとき A の複製が途中までしか届いていなければ、ack 済みのデータを失うことになる。だからこそ、上の「ack は複製の後」が重要になる。

## 決定論的シミュレーション: 同じ入力なら同じ結果になるテスト

ここまでの仕組みは、タイミングによって壊れる。「A のリース更新がバケットに届く直前に B が期限切れを見た」のような、ナノ秒の隙間で起きる競合だ。実機で再現するのはほぼ不可能なので、celld は協調ロジックを**時計もネットワークも持たない純粋な関数**として書き、テストがその外側から時刻や通信結果を好きな順で与える。同じ順で与えれば同じ結果になる (決定論的) ので、失敗したら同じ順を再現して調べられる。[決定コアのページ](../decision-core/) と [決定論の境界のページ](../deterministic-boundary/) が扱う。

## 用語集

| 言葉                     | 意味                                                                         |
| ------------------------ | ---------------------------------------------------------------------------- |
| ノード                   | celld のプロセスが動いているサーバー 1 台                                    |
| セル                     | 状態を持つ小さな単位。1 セル = 1 SQLite。Cloudflare でいう Durable Object    |
| バケット                 | S3 / GCS / Azure Blob のオブジェクトストレージ。データ保管と調停の両方に使う |
| 所有権                   | あるセルを担当する権利。1 セルにつき 1 ノード                                |
| 所有権レコード           | `cells/<セル>/own.json`。担当ノードとエポックを持つ                          |
| 条件付き書き込み (CAS)   | 「無いときだけ作る」「読んだ版から変わっていなければ上書きする」書き込み     |
| etag                     | オブジェクトの版を表す文字列。`If-Match` の条件に使う                        |
| エポック                 | 担当が決まるたびに 1 増える番号。フェンシングトークン                        |
| フェンシング             | 古い所有者の書き込みを無害にする仕組みの総称                                 |
| 古い所有者 (stale owner) | 担当を外されたことに気づかず動いているノード                                 |
| 二重所有 (split-brain)   | 1 セルを 2 ノードが同時に担当している事故                                    |
| リース                   | 「生きている」の期限付き宣言。`nodes/<ノード>.json`                          |
| self-fence               | リースを失ったノードが自分で停止すること                                     |
| 曖昧 / 確定              | 書けたか分からないエラー / 書けていないと確定したエラー                      |
| ack                      | クライアントへの「保存しました」という返事                                   |
| RPO=0                    | ack したデータを 1 件も失わないという保証                                    |
| 複製                     | セルの SQLite をバケットへコピーすること。celld では LTX という形式を使う    |
| 出力ゲート               | 複製が終わるまでクライアントへの返事を止める仕組み                           |
| テイクオーバー           | 死んだノードのセルを別ノードが引き継ぐこと                                   |
| リストア                 | バケットの複製からセルの SQLite を組み立て直すこと                           |
| 決定論的シミュレーション | 時刻と通信結果を外から与え、同じ入力で同じ結果になる形のテスト               |
