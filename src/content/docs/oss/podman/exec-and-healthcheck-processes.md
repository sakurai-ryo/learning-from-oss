## 何を学んだか

### exec もコンテナ起動と同じ形

`podman exec -it web bash` を実行すると、`podman` プロセスは **conmon をもう 1 つ起動する**。その conmon が `crun exec` を呼び、`bash` の親になる。

```
systemd
├─ conmon (コンテナ本体)
│  └─ nginx: master process
└─ conmon (exec セッション)
   └─ bash
```

つまり **コンテナ起動と exec は同じ仕組みの使い回し** だ。違いは conmon に渡す引数だけで、`-e` (exec モード)、`--exec-attach`、`--exec-process-spec <path>` が付く。`process-spec` は OCI Runtime Spec の `process` 部分だけを書いた JSON ファイルで、`config.json` の一部と同じ形をしている。

デーモンがあれば、exec は「デーモンに頼んで既存のコンテナに入る」で済む。デーモンレスでは **「新しいプロセスを立てて、既存のコンテナに合流させる」** 必要があり、そのための親役がもう 1 つ要る。

### exec セッションは DB に載る

exec は使い捨てに見えるが、状態を持つ。`podman exec -d` (デタッチ) したセッションの終了コードを後から取れる必要があるし、コンテナを削除するときには走っている exec を止める必要がある。

そこで `ExecSession` が DB に保存される。持っているのは ID、コンテナ ID、状態、PID、終了コード、設定、そして **`PIDData`** という耳慣れないフィールドだ。

### PID は再利用される

ここに、デーモンレス設計の根本的な問題が出る。

デーモンなら、起動した子プロセスの `wait()` を握っているので「その PID は自分の子である間、他のプロセスに再利用されない」ことが保証される。Podman は違う。**PID を DB に書いて終了する**。次に `podman exec --help` で状態を見るプロセスは、その PID を読み直す。

その間にプロセスが終了し、PID が別のプロセスに再割り当てされていたら？ Podman は「まだ走っている」と誤認し、最悪の場合 **無関係なプロセスにシグナルを送る**。

Podman の解決策が `pkg/pidhandle` だ。「この PID は、記録したときと同じプロセスか」を確かめられる **文字列** を作って DB に一緒に保存する。

- **`pidfd_open(2)`** でプロセスへの fd を取り、
- **`name_to_handle_at(2)`** でその fd を安定した識別子 (file handle) に変換し、
- 16 進文字列にして保存する

後で読み直すときは、この文字列から fd を復元する。PID が再利用されていれば復元に失敗するか、別のハンドルになるので検出できる。

対応していないカーネルでは **プロセスの起動時刻** をフォールバックに使う。`/proc/<pid>/stat` の starttime が一致しなければ別プロセス、という判定だ。

## ソースコードのどこか

### exec 用の conmon 引数

[`libpod/oci_conmon_exec_common.go#L415-L419`](https://github.com/podman-container-tools/podman/blob/v6.1.0/libpod/oci_conmon_exec_common.go#L415)。

```go title="libpod/oci_conmon_exec_common.go"
	// Append container ID and command
	args = append(args, "-e")
	// TODO make this optional when we can detach
	args = append(args, "--exec-attach")
	args = append(args, "--exec-process-spec", processFile.Name())

	if len(options.ExitCommand) > 0 {
		args = append(args, "--exit-command", options.ExitCommand[0])
		for _, arg := range options.ExitCommand[1:] {
			args = append(args, []string{"--exit-command-arg", arg}...)
		}
		if options.ExitCommandDelay > 0 {
			args = append(args, []string{"--exit-delay", strconv.FormatUint(uint64(options.ExitCommandDelay), 10)}...)
		}
	}
```

コンテナ起動と同じく `--exit-command` を渡す。exec セッションが終了したら、**新しい `podman` プロセスが起動して後始末をする**。デタッチした exec の終了コードが DB に記録されるのは、この仕組みによる。

`--exit-delay` があるのが目を引く。exec の終了直後に片付けると、まだ終了コードを読んでいないクライアントが取り逃す。少し待たせる余地を持たせている。

### ExecSession が PIDData を持つ

[`libpod/container_exec.go#L93-L115`](https://github.com/podman-container-tools/podman/blob/v6.1.0/libpod/container_exec.go#L93)。

```go title="libpod/container_exec.go"
type ExecSession struct {
	// Id is the ID of the exec session.
	// Named somewhat strangely to not conflict with ID().
	Id string `json:"id"`
	// ContainerId is the ID of the container this exec session belongs to.
	ContainerId string `json:"containerId"`

	// State is the state of the exec session.
	State define.ContainerExecStatus `json:"state"`
	// PID is the PID of the process created by the exec session.
	PID int `json:"pid,omitempty"`
	// ExitCode is the exit code of the exec session, if it has exited.
	ExitCode int `json:"exitCode,omitempty"`

	// Config is the configuration of this exec session.
	// Cannot be empty.
	Config *ExecConfig `json:"config"`

	// PIDData is a string uniquely identifying the PID. The value is platform
	// specific. It is generated by pidhandle package and used by isSessionAlive.
	PIDData string `json:"pidData,omitempty"`
}
```

`PID` の隣に `PIDData` がある。「**PID を一意に識別する文字列**。プラットフォーム固有で、`pidhandle` パッケージが生成し、`isSessionAlive` が使う」。

`json` タグが付いているので、この文字列はそのまま SQLite の JSON カラムに入る ([状態を SQLite に置く](../sqlite-state/))。

### PIDHandle の意図がインターフェースのコメントに書いてある

[`pkg/pidhandle/pidhandle.go#L15-L23`](https://github.com/podman-container-tools/podman/blob/v6.1.0/pkg/pidhandle/pidhandle.go#L15)。

```go title="pkg/pidhandle/pidhandle.go"
// PIDHandle defines an interface for working with operating system processes
// in a reliable way. OS-specific implementations include additional logic
// to try to ensure that operations (e.g., sending signals) are performed
// on the exact same process that was originally referenced when the PIDHandle
// was created via NewPIDHandle or NewPIDHandleFromString.
//
// This prevents accidental interaction with a different process in scenarios
// where the original process has exited and its PID has been reused by
// the system for an unrelated process.
type PIDHandle interface {
	// Returns the PID associated with this PIDHandle.
	PID() int
	// Releases the PIDHandle resources.
	Close() error
	// Sends the signal to process.
	Kill(signal unix.Signal) error
	// Returns true in case the process is still alive.
	IsAlive() (bool, error)
	// Returns a serialized representation of the PIDHandle.
	// This string can be passed to NewPIDHandleFromString to recreate
	// a PIDHandle that reliably refers to the same process as the original.
	String() (string, error)
}
```

**「元のプロセスが終了し、PID が無関係なプロセスに再利用された場合に、誤って別のプロセスを操作してしまうのを防ぐ」**。目的が 1 文で書かれている。

そして `String()` / `NewPIDHandleFromString` という **シリアライズ可能なハンドル** が要のメソッドだ。ハンドルをプロセス間・実行間で運べるので、デーモンレスでも「同じプロセスか」を検証できる。

### pidfd を file handle に変換する

[`pkg/pidhandle/pidhandle_linux.go#L177`](https://github.com/podman-container-tools/podman/blob/v6.1.0/pkg/pidhandle/pidhandle_linux.go#L177)。

```go title="pkg/pidhandle/pidhandle_linux.go"
func (h *pidfdHandle) String() (string, error) {
	if len(h.normalHandle.pidData) != 0 {
		return h.normalHandle.pidData, nil
	}

	// Serialize the pidfd to string if possible.
	if h.pidfd > -1 {
		fh, _, err := nameToHandleAt(h.pidfd, "", unix.AT_EMPTY_PATH)
		if err != nil {
			// Do not fail if NameToHandleAt is not supported, we will
			// fallback to process start-time later.
			if err == unix.ENOTSUP {
				logrus.Debugf("NameToHandleAt(%d) failed: %v", h.pidfd, err)
			} else {
				return "", err
			}
		} else {
			hexStr := hex.EncodeToString(fh.Bytes())
			return nameToHandlePrefix + strconv.Itoa(int(fh.Type())) + " " + hexStr, nil
		}
	}

	// Fallback to default String().
	return h.normalHandle.String()
}
```

`name_to_handle_at` は本来ファイルシステム上のファイルを一意に識別するための syscall だが、**pidfd に対して使うと「そのプロセスを指す安定したハンドル」が得られる**。それを 16 進化して `name-to-handle:<type> <hex>` という文字列にする。

段階的な縮退も丁寧だ。

```go title="pkg/pidhandle/pidhandle_linux.go"
	pidfd, err := pidfdOpen(pid, 0)
	if err != nil {
		switch err {
		case unix.ENOSYS:
			// Do not fail if PidFdOpen is not supported, we will
			// fallback to process start-time later.

		case unix.ESRCH:
			// The process does not exist, so any future call of Kill
			// or IsAlive should return unix.ESRCH, even if the pid is
			// recycled in the future. Let's note it in the pidData.
			pidData = noSuchProcessID
```

- `ENOSYS` (カーネルが `pidfd_open` を持たない) → 起動時刻フォールバック
- `ESRCH` (プロセスが既に無い) → **`"no-proc"` という文字列を記録** して、以降どんなに PID が再利用されても「無い」と答える
- `EINVAL` → PID が無効、または既に再利用されたとみなす

3 種類の errno に、それぞれ違う意味と対処が割り当てられている。

そして関数のコメントには残る競合も書いてある。

```go title="pkg/pidhandle/pidhandle_linux.go"
// Creates new PIDHandle for a given process pid.
//
// Note that there still can be a race condition if the process terminates
// *before* the PIDHandle is created. It is a caller's responsibility
// to ensure that this either cannot happen or accept this risk.
```

**「PIDHandle を作る前にプロセスが終了した場合の競合は残る。呼び出し側の責任」**。解けない部分を隠さず明示している。

### ヘルスチェックも exec の上に載る

`podman healthcheck run <container>` は、systemd の transient timer から定期的に起動される ([transient timer](../systemd-healthcheck/))。その中身は **コンテナに対する exec** だ。

つまりヘルスチェック 1 回ごとに、

1. systemd の timer が `podman healthcheck run` を起動
2. その `podman` が `libpod.Runtime` を初期化
3. exec セッションを作り、conmon を起動
4. conmon が `crun exec` でヘルスチェックコマンドを実行
5. 結果を JSON ファイルに書いて全部終了

というプロセスの連鎖が走る。デーモンなら「ゴルーチン 1 本 + exec」で済むところに、プロセスが 3 つ立つ。**デーモンレスのコストが最も見えやすい箇所** といえる。

代わりに得られるのは、ヘルスチェックが systemd の管理下にあること、失敗しても他に波及しないこと、そして `podman` プロセスが 1 つも常駐していない状態でもヘルスチェックが回り続けることだ。

## なぜそうなっているか

### PID を状態として持つ設計は、必ず再利用問題にぶつかる

「プロセス ID を DB に保存して、後で生死を確かめる」は、デーモンレスなら避けられない。そして PID は 32768 でラップして再利用される。コンテナを頻繁に起動するホストでは、数時間で一周することもある。

伝統的な回避策は「PID + 起動時刻」の組で識別することだった。`/proc/<pid>/stat` の 22 番目のフィールドを比べる。これは今もフォールバックとして残っている。

`pidfd` はより確実で、Linux 5.3 以降で使える。だが **fd はプロセスを跨げない**。Podman は起動のたびに別プロセスなので、fd をそのまま持ち越せない。そこで `name_to_handle_at` で fd を「文字列にできるハンドル」に変換する、という一手が入る。

**デーモンなら fd をそのまま持っていればよい問題を、シリアライズ可能な形にする必要があった** ということだ。デーモンレスの制約が、そのまま実装のアイデアを要求している。

### exec に conmon を使い回したのは、要求が同じだから

exec も「プロセスの親であり続け、stdio を中継し、終了コードを記録する」という要求はコンテナ起動と同じだ。別の仕組みを作る理由がない。

conmon 側に `-e` フラグと `--exec-process-spec` を足すだけで済んだのは、**conmon の責務が「OCI ランタイムを呼んで親になる」に絞られていた** から。責務が狭いものは再利用が効く。

## どう活かすか

- **PID をプロセス間で受け渡すなら、識別子を添える。** PID 単体は再利用される。`pidfd` + `name_to_handle_at`、あるいは起動時刻の組み合わせで「同じプロセスか」を検証できるようにする。これは Podman に限らず、pid ファイルを使うすべてのツールに当てはまる。
- **fd をシリアライズしたくなったら `name_to_handle_at` を思い出す。** 本来はファイル用だが、pidfd にも効く。プロセスを跨いで参照を運ぶ手段として使える。
- **解けない競合は、コメントで呼び出し側に渡す。** 「ハンドルを作る前に死んだ場合の競合は残る、呼び出し側の責任」と書いてあることで、上位が対処を検討できる。隠すと誰も気づかない。
- **errno ごとに意味を割り当てる。** `ENOSYS` は縮退、`ESRCH` は確定的な「無い」、`EINVAL` は再利用の疑い。まとめて「エラー」にすると、この区別が失われる。
- **責務が狭い部品は再利用が効く。** conmon が「OCI ランタイムを呼んで親になる」だけだったから、exec に転用できた。責務を広げるほど、次の用途で使えなくなる。
