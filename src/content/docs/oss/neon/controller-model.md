## 何を学んだか

storage_controller の役割は、`docs/storage_controller.md` の 1 文に集約されている。

```markdown title="docs/storage_controller.md"
The storage controller also manages generations, high availability (via secondary locations) and live migrations for tenants under its management. This is done with a reconciliation loop pattern, where tenants have an “intent” state and a “reconcile” task that tries to make the outside world match the intent.
```

([docs/storage_controller.md](https://github.com/neondatabase/neon/blob/fa504217c61bbcaf5c512d75830564541f917f8f/docs/storage_controller.md))

**Kubernetes のコントローラと同じ構造**だ。ただし対象が Pod ではなく tenant shard の配置になっている。

中心の型はこうなる。

```rust title="storage_controller/src/tenant_shard.rs"
pub(crate) struct TenantShard {
    pub(crate) tenant_shard_id: TenantShardId,

    pub(crate) shard: ShardIdentity,

    // Latest generation number: next time we attach, increment this
    // and use the incremented number when attaching.
    pub(crate) generation: Option<Generation>,

    // High level description of how the tenant should be set up.  Provided
    // externally.
    pub(crate) policy: PlacementPolicy,

    // Low level description of exactly which pageservers should fulfil
    // which role.  Generated by `Self::schedule`.
    pub(crate) intent: IntentState,

    // Low level description of how the tenant is configured on pageservers:
    // if this does not match `Self::intent` then the tenant needs reconciliation
    // with `Self::reconcile`.
    pub(crate) observed: ObservedState,
```

([storage_controller/src/tenant_shard.rs L59](https://github.com/neondatabase/neon/blob/fa504217c61bbcaf5c512d75830564541f917f8f/storage_controller/src/tenant_shard.rs#L59))

**3 層になっている。**

| 層         | 内容                                           | 誰が決めるか         |
| ---------- | ---------------------------------------------- | -------------------- |
| `policy`   | 「attached 1 + secondary 1 が欲しい」          | 外部 (control plane) |
| `intent`   | 「attached はノード 5、secondary はノード 12」 | Scheduler            |
| `observed` | 「ノード 5 に attached として設定済み」        | Reconciler の結果    |

Kubernetes だと `spec` と `status` の 2 層だが、ここでは**「何が欲しいか」と「どこに置くか」が分かれている。** 配置の決定 (scheduling) が独立した段になっていて、それ自体をテストできる。

## 観測状態には「分からない」がある

```rust title="storage_controller/src/tenant_shard.rs"
/// Our latest knowledge of how this tenant is configured in the outside world.
///
/// Meaning:
///     * No instance of this type exists for a node: we are certain that we have nothing configured on that
///       node for this shard.
///     * Instance exists with conf==None: we *might* have some state on that node, but we don't know
///       what it is (e.g. we failed partway through configuring it)
///     * Instance exists with conf==Some: this tells us what we last successfully configured on this node,
///       and that configuration will still be present unless something external interfered.
pub(crate) struct ObservedStateLocation {
```

([storage_controller/src/tenant_shard.rs L401](https://github.com/neondatabase/neon/blob/fa504217c61bbcaf5c512d75830564541f917f8f/storage_controller/src/tenant_shard.rs#L401))

**3 値論理になっている。**

- **エントリなし** — 確実に何もない
- **エントリあり + `conf == None`** — 何かあるかもしれないが、分からない
- **エントリあり + `conf == Some`** — こう設定した

真ん中が本質的だ。**リモート呼び出しがタイムアウトしたとき、相手に何が起きたかは分からない。** 届いて実行されたかもしれないし、届かなかったかもしれない。

2 値 (ある / ない) で表現すると、この状態を「ない」に丸めることになる。すると後始末が漏れる。「あるかもしれない」を明示的に持てば、**次の reconcile で detach を試みる**という正しい動作になる。

**分散システムで「分からない」を型に持たないと、必ず取りこぼす。**

([storage_controller/src/tenant_shard.rs L197](https://github.com/neondatabase/neon/blob/fa504217c61bbcaf5c512d75830564541f917f8f/storage_controller/src/tenant_shard.rs#L197))

**intent を変えると、必ず scheduler の集計が更新される。** `IntentState` のフィールドが private で、setter が `&mut Scheduler` を要求するので、**集計を更新せずに intent を変えることが型として不可能**になっている。

scheduler は「各ノードに何個の shard が載っているか」を持っていて、それが配置の判断材料になる ([シャードをどのノードに置くか](../scheduler/))。この集計を再計算すると O(全 shard) かかるので、差分で維持したい。**差分更新の整合性を、API の形で守っている。**

## DB に書かないものを決める

RFC の「Durability」の節が、この設計で最も特徴的な部分だ。

```markdown title="docs/rfcs/2025-02-14-storage-controller.md"
We rely on an external postgres for all durable state. No local storage is used.

We avoid any unnecessary I/O to durable storage. For example:

- most tracking of in-flight changes to the system is done in-memory rather than recording progress/steps in a database
- When migrating tenant shards between pageservers we only touch the database to increment generation numbers,
  we do not persist the total state of a tenant shard.
```

([docs/rfcs/2025-02-14-storage-controller.md](https://github.com/neondatabase/neon/blob/fa504217c61bbcaf5c512d75830564541f917f8f/docs/rfcs/2025-02-14-storage-controller.md))

**「移行中は generation の更新以外 DB を触らない」。**

なぜそれで済むのか。**generation さえ正しければ、他は間違っても安全だから**だ ([generation 番号](../generations-and-deletion/))。移行が中途半端に終わっても、データは壊れない。次の reconcile でやり直せばいい。

**「壊れたら困る状態」だけを DB に置き、「間違っても再導出できる状態」はメモリに置く。** その線引きが generation で引かれている。

secondary の配置がその典型例になる。

```markdown title="docs/rfcs/2025-02-14-storage-controller.md"
For example, we do not store the secondary pageserver locations of tenant shards in the database, rather we learn these at startup from running pageservers, and/or make scheduling decisions to fill in the gaps. This adds some complexity, but massively reduces the load on the database, and enables running the storage controller with a very cheap postgres instance.
```

**secondary の場所は DB に書かない。起動時に pageserver に聞く。** secondary は読み書きしないので、間違っても壊れない ([ディスクが足りなくなったとき](../eviction-and-secondary/))。

そして目的が「安い Postgres インスタンスで動かせるようにする」と明記されている。**運用コストが設計判断の直接の理由になっている。**

## 巨大なロック 1 つ

```markdown title="docs/rfcs/2025-02-14-storage-controller.md"
The state is held in a `ServiceInner` wrapped in a RwLock. This monolithic
lock is used to simplify reasoning about code that mutates state: each function that takes a write lock may be thought of as a serializable transaction on the in-memory state. This lock is clearly a bottleneck, but
nevertheless is scalable to managing millions of tenants.
```

**全状態を 1 つの `RwLock` に入れる。** 「明らかにボトルネックだが、数百万テナントまでは持つ」。

得られるのは**推論のしやすさ**だ。書き込みロックを取る関数は、直列化可能なトランザクションだと思ってよい。細かいロックに分けると、順序の問題とデッドロックが出る ([page_cache](../page-cache/) の 2 段ロックがまさにそれだ)。

「millions of tenants までスケールする」という主張は、ロックの中でやることが**メモリ上の構造の更新だけ**であることに依っている。I/O は全部ロックの外で起きる。

Reconciler が Service の状態にアクセスできないのも、この設計から来ている。

```markdown title="docs/rfcs/2025-02-14-storage-controller.md"
Reconciler does not have access to the `Service` state: it is populated with a snapshot of relevant information when constructed, and submits is results to a channel that `Service` consumes to update the tenant shard's observed state.
```

**スナップショットを渡して、結果はチャネルで返す。** ロックを持ったまま I/O をしない、を構造として強制している。

## 限界に達したらセルを増やす

```markdown title="docs/rfcs/2025-02-14-storage-controller.md"
When the practical scale limit of a single storage controller is reached, just deploy another one with its
own pageservers & safekeepers: each controller+its storage servers should be thought of as a logical cluster
or "cell" of storage.
```

**1 つのコントローラをスケールさせるのではなく、コントローラごと複製する。**

これは分散システムの設計として重要な選択だ。コントローラを分散させると、コントローラ自体の合意が要る。セル分割なら、各セルは独立して単純なままでいられる。

代償は、セルをまたぐ移行ができないことと、セルの割り当てを誰かが決めなければならないこと。**複雑さを 1 段上に押し上げている。**

## 起動時の O(N)

```markdown title="docs/rfcs/2025-02-14-storage-controller.md"
There are places where we do O(N) work:

- On normal startup, when loading from the database into memory
- On unclean startup (with no handover of observed state from a previous controller), where we will
  scan all shards on all pageservers.

It is important that these locations are written efficiently. At high scale we should still expect runtimes
of the order tens of seconds to complete a storage controller start.
```

**「起動に数十秒かかることを想定すべき」。** インメモリのシステムを選んだ代償が、そのまま起動時間になる。

そして「前のコントローラから観測状態を引き継げなかった場合」は、全 pageserver の全 shard を走査する。これがゼロダウンタイムのデプロイを必要にしている ([リーダー交代とノード障害検知](../leadership-and-heartbeat/))。

## この先に効いてくること

- **policy / intent / observed の 3 層。** 配置の決定を独立した段にすると、テストできる。
- **観測状態に「分からない」を持つ。** リモート呼び出しの結果が不明なとき、それを型で表す。
- **DB に書くのは「壊れたら困る状態」だけ。** 再導出できるものはメモリに置く。
- **巨大なロック 1 つは、推論のしやすさと引き換えに取ってよいことがある。** ただし I/O をロックの外に出すこと。
- **スケール限界はセル分割で越える。** コントローラ自体は分散させない。
