## 何を学んだか

SQLite のパーサは **lemon** という LALR パーサジェネレータが `parse.y` から生成する。文法をファイルで宣言すれば、パーサのコードが出てくる。

Turso はそれを引き継がなかった。

```text title="AGENTS.md"
| SQL parsing | `sqlite/parser/src/parser.rs` | 11k LOC recursive descent |
```

**手書きの再帰下降パーサ。** 現在は 13,381 行あり、うち 5,414 行がパーサ本体、残り 7,967 行が同じファイル内のテストになっている。

出自は lemon の系譜に残っている。

```rust title="sqlite/parser/src/token.rs"
/// Token classes
// Generated by lemon (parse.h).
// Renamed manually.
// To be keep in sync.
```

[`sqlite/parser/src/token.rs#L3-L6`](https://github.com/tursodatabase/turso/blob/34b38a1a43a4449b868141c62508ab0c8376308b/sqlite/parser/src/token.rs#L3-L6)。

**トークン型の一覧だけは lemon の生成物から取り、手で名前を付け替えて、以降は手で同期する。** 文法の実装は手書きだが、**語彙は参照実装と共有している。**

手書きにした理由は [次のページ](../context-keywords/) で扱う。ここでは、手書きにした結果どうなったかを見る。

## ソースコードのどこか

### 期待するトークンから、エラーメッセージが自動で作られる

手書きパーサで最も繰り返される処理は「次のトークンがこれらのどれかであることを確かめる」だ。それがマクロになっている。

```rust title="sqlite/parser/src/parser.rs"
                $($x => token,)*
                tt => {
                    ...

                                parsed_offset: ($parser.offset(), token_len).into(),
                                expected: &[
                                    $($x,)*
```

[`sqlite/parser/src/parser.rs#L23-L51`](https://github.com/tursodatabase/turso/blob/34b38a1a43a4449b868141c62508ab0c8376308b/sqlite/parser/src/parser.rs#L23-L51)。

**マクロに渡したトークンの一覧が、そのままエラーの `expected` になる。**

パーサジェネレータの利点の 1 つは、**文法から「ここで来られるトークンの集合」が自動的に導ける**ことだ。手書きだとその情報が失われる。

このマクロは、**呼び出し側が既に書いているトークンの一覧を再利用して、それを取り戻している。** `eat_expect!(self, TK_PRECEDING, TK_FOLLOWING)` と書けば、失敗時に「`PRECEDING` または `FOLLOWING` を期待したが `X` が来た」と出る。

整形も専用の関数がある。1 個なら「X」、2 個なら「X or Y」、3 個以上なら「X, Y, or Z」。そして `TK_ID` は「identifier」、`TK_PTR` は「->」のように、**内部の識別子ではなく人間向けの名前に変換される** ([`user_friendly_name`](https://github.com/tursodatabase/turso/blob/34b38a1a43a4449b868141c62508ab0c8376308b/sqlite/parser/src/token.rs#L596-L619))。

**`match` の分岐に入った時点で、トークンの型は確定している。** そこでもう一度検査するのは無駄だが、**書き間違いは起こりうる**。だから debug ビルドだけで見張る。

**「呼び出し側が保証すべきこと」と「利用者の入力に対して検査すべきこと」を、別のマクロに分けている。** 前者を `Result` にすると、ありえないエラー経路が全体に増える。

### 深さの制限が 2 つある

再帰下降パーサの古典的な弱点は、**深くネストした入力でスタックが溢れる**ことだ。`((((((...1...))))))` を書けば落ちる。

対策は素直に見える。

```rust title="sqlite/parser/src/parser.rs"

    /// `last_expr_height` holds the height of the returned expression.

                "Expression tree is too large (maximum depth {MAX_EXPR_DEPTH})"
            )));

```

**`a OR b OR c OR ...` は、優先順位登りのループが `while` で消費する。再帰は 1 段しか深くならない。**

だが **できあがる木は左に深い。** `Or(Or(Or(a, b), c), d)` という形で、要素が 1 万個あれば高さ 1 万の木になる。

**パーサは無事に通る。落ちるのはその木を再帰的に歩く後段だ。**

だから木の高さを別に数える。

### 上限値の根拠が、パーサの外にある

```rust title="sqlite/parser/src/parser.rs"
/// Maximum query expression depth, our equivalent of SQLite's
/// `SQLITE_MAX_EXPR_DEPTH` (default 1000). Kept lower because our recursive
/// translator/optimizer uses larger stack frames per nesting level, so a
/// 1000-deep tree still overflows a default 8 MiB thread stack in debug builds.
pub const MAX_EXPR_DEPTH: usize = 100;
```

[`sqlite/parser/src/parser.rs#L185-L189`](https://github.com/tursodatabase/turso/blob/34b38a1a43a4449b868141c62508ab0c8376308b/sqlite/parser/src/parser.rs#L185-L189)。

**SQLite の既定は 1000。Turso は 100。**

理由が明快だ。**「翻訳器とオプティマイザが、ネスト 1 段あたりに使うスタックフレームが大きい。だから深さ 1000 の木は、debug ビルドの既定 8MiB スタックを溢れさせる。」**

**パーサの制限値が、パーサの都合ではなく消費者の都合で決まっている。** 導入したコミットのタイトルがそれを裏書きしている。

```text
8011555c6 sqlite/parser: bound expression depth to prevent translator stack overflow
```

同じ理由で、型のネストにも別のカウンタがある (`type_nesting_depth`)。**深い再帰を生む構文ごとに、独立した上限を持つ。**

**表と実装がずれている 2 箇所には、その場に理由が書いてある。** `NOT` は表では 2 だが実装では 3 (二項演算子として現れる場合のため)、`ESCAPE` は表では 5 だが実装では優先順位を持たない (`LIKE` の解析後に消費されるため)。

**表を自分の言葉で書き直していたら、このずれは見えなくなる。**

左結合は `pre + 1` で表現される。


右側を「自分より 1 高い優先順位」で解析すると、同じ優先順位の演算子が右に取り込まれなくなる。**`BETWEEN` だけは `start` を `pre`、`end` を `pre + 1` で解析する。** `x BETWEEN a AND b IS NOT NULL` で `IS NOT NULL` が `b` ではなく `BETWEEN` 全体に付くようにするためだ。

### 失敗したら位置を巻き戻す


**3 種類のパラメータが、1 つの番号空間を共有する。**

- `?` — 出現順に次の番号
- `?N` — 明示された番号。**カウンタをその値まで押し上げる**
- `:name` / `@name` / `$name` — 同じ名前は同じ番号。初出のときだけ採番

`?N` がカウンタを押し上げるので、`SELECT ?5, ?` の 2 つ目は `?6` になる。**SQLite の仕様どおりの挙動**で、知らなければまず実装しない。

つまり **パーサは状態を持つ。** 純粋な「トークン列 → 木」の変換ではない。その状態は文ごとにリセットされる。

**`near "X": syntax error` は SQLite の構文エラーの文言そのまま。** [互換性の契約](../sqlite-compat/) がここにも効いていて、エラーメッセージで分岐しているアプリケーションが壊れない。

そのうえで、**miette の `help` として「何を期待していたか」を別に出し、`#[label("here")]` で入力のどこかを指す。**

**「互換の部分」と「改善の部分」を、同じエラーの中で別の枠に分けている。** 本文を改善すると互換が壊れるが、補助情報を足すのは壊さない。

字句解析側のエラーも同様に細かく分かれている。「文字列が閉じていない」「`]` がない」「`*/` がない」「数値の指数部が壊れている」が、それぞれ別のバリアントになっていて、**「構文エラー」に潰していない** ([`error.rs`](https://github.com/tursodatabase/turso/blob/34b38a1a43a4449b868141c62508ab0c8376308b/sqlite/parser/src/error.rs))。

## なぜそうなっているか

- **パーサジェネレータをやめて手書きにしたのは、文脈依存の判断が多すぎるから** ([次のページ](../context-keywords/))。lemon の `%fallback` で扱えないケースが 10 個以上ある。
- **トークン型だけ lemon の生成物を引き継いだのは、語彙が参照実装と一致していてほしいから。** 文法の実装は変えても、トークンの分類がずれると `EXPLAIN` の比較まで影響する。
- **期待トークンをマクロの引数から拾うのは、生成器なら自動で得られる情報だから。** 手書きにすると失われるものを、既に書いてある情報から取り戻している。
- **「確認済みを取り出す」と「確認してから取り出す」を分けたのは、ありえないエラー経路を増やさないため。** `match` の分岐に入った時点で確定しているものを `Result` にすると、呼び出し側全部に無意味な `?` が要る。
- **再帰の深さと木の高さを別々に数えるのは、両者が一致しないから。** 左結合の連鎖はループで消費されるので再帰は深くならないが、木は伸びる。**パーサが無事でも後段が落ちる。**
- **上限が SQLite の 1/10 なのは、後段のスタック消費が大きいから。** 制限値をパーサの都合で決めると、消費者が落ちる。
- **優先順位表を原文のまま貼ったのは、ずれを見えるようにするため。** 自分の言葉で書き直すと、実装との差分が消える。
- **`mark` の保存対象が 3 つで済むのは、状態が入力位置に集約されているから。** 木は戻り値なので、失敗すれば自然に捨てられる。
- **パーサが `Iterator` なのは、複数文の入力を 1 文ずつ処理したいから。** そして失敗時に位置が戻るので、別の方言で再挑戦できる。
- **パラメータ番号をパーサが振るのは、割り当てが出現順に依存するから。** 後段では「何番目に現れたか」が分からない。
- **エラーの本文を SQLite と同じにしたのは、文言で分岐するアプリがあるから。** 改善は `help` という別の枠に置く。

## どう活かすか

- **パーサジェネレータを使うか手書きにするかは、文法の性質で決める。** 文脈依存の判断が多い文法では、生成器の枠に収めるコストが手書きを上回ることがある。
- **手書きにするなら、生成器が無料でくれていた情報を明示的に取り戻す。** 「ここで来られるトークンの集合」は、エラーメッセージの質をそのまま決める。
- **内部の識別子を、利用者に見せるメッセージにそのまま出さない。** 対応表 1 つで、エラーの読みやすさが変わる。
- **「呼び出し側が保証すべき前提」と「入力に対する検査」を、別の道具に分ける。** 前者を `Result` にすると、ありえないエラー経路がコード全体に生える。前者は debug ビルドの assert で十分になる。
- **再帰的な構造を作るときは、「再帰の深さ」と「できあがる構造の深さ」を別に測る。** 反復で構築した構造が深くなることは普通にある。
- **深さの上限は、その構造を最も深く辿る消費者に合わせる。** 作る側の都合で決めると、使う側が落ちる。
- **参照する仕様の表は、原文のまま貼って、ずれる箇所にだけ注釈を付ける。** 書き直すと、実装との差分が見えなくなる。
- **巻き戻しが必要なら、状態を「入力の位置」に集約する。** 出力が戻り値なら、失敗時に捨てるものが自然に決まる。
- **エラーは、互換のために固定する部分と、改善してよい部分に分ける。** 本文は変えず、補助情報を別枠で足す。
- **エラーの種類を、原因ごとに分ける。** 「構文エラー」に潰すと、直し方が読み取れない。
- **境界値には、下限の 1 つ下・上限の 1 つ上・上限ちょうどのテストを書く。** 上限の値は特に間違えやすい。
