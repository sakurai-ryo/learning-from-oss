InfluxDB 3 Core は、時系列データを取り込んで SQL / InfluxQL でクエリできるデータベースだ。書き込みは line protocol で受け、1 秒ごとに WAL としてオブジェクトストアに書き、数分ごとに Parquet に固める。クエリは Apache DataFusion が実行し、メモリバッファと Parquet の両方を読む。

v1 / v2 とは実装が完全に別で (Go から Rust へ)、この章が扱うのは `main` ブランチの v3 系列だけを指す。

## この OSS について

- InfluxData が開発。MIT または Apache 2.0 のデュアルライセンス。Rust 2024 edition。
- `influxdb3_*` の各クレートが約 18 万行 (テストを除くと約 9.6 万行)。加えて `core/` に InfluxDB 3 の共通基盤 (旧 IOx) が約 21 万行入っていて、DataFusion 拡張・オブジェクトストアのラッパ・実行環境がここにある。
- **ローカルディスクを前提にしない設計** が全体を貫いている。WAL、カタログ、データ、インデックスのすべてがオブジェクトストア上のオブジェクトで、そこには追記も、ロックも、セカンダリインデックスも無い。この制約に対する answer が、章の大半を占める。
- **Apache Arrow エコシステムへの徹底した相乗り** も特徴だ。クエリ実行は DataFusion、永続化形式は Parquet、メモリ上の表現は Arrow。ソートと重複排除は自前で書かず、DataFusion の COMPACT プランを書き込みパスから呼ぶ。専用キャッシュは「テーブル関数」として SQL に生やす。
- コメントの質が高い。「なぜこの順序なのか」「この関数が失敗しないと言える根拠」「この定数の由来」「未解決の設計判断とその issue 番号」が、コードの隣に書かれている。この章の引用の多くは、その手のコメントそのものだ。

## 読む順番

RDB の内部構造には馴染みがあるが InfluxDB は初めて、という場合は [前提のページ](./architecture/) から読んでほしい。データモデルとアーキテクチャを RDB の言葉との対応で説明していて、他のページが使う語彙 (WAL、カタログ、gen1 チャンク、スナップショット) はすべてここで導入する。慣れていれば、末尾の用語対応表だけ眺めて飛ばして構わない。

「ストレージ」の 5 ページは前から順に読むのがよい。書き込みが WAL になり、いつ永続化するかが決まり、メモリ上でどう保持され、どこに置かれ、どう受け渡されるか、という 1 本の流れになっている。

「カタログ」は独立して読めるが、CAS のページ (7) はログとチェックポイントのページ (6) を前提にしている。

「クエリ実行」と「プロセス運用」はどこからでも読める。運用の 3 ページは、DB 固有の話が少ないぶん、他のシステムにそのまま持ち込みやすい。
