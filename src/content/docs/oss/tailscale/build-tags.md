## 何を学んだか

### なぜバイナリを削るのか

`tailscaled` は、ルータ、NAS、組み込み機器でも動く。**フラッシュメモリが 16 MB しかない機器** もある。

だが Tailscale には機能が多い。ACME の証明書取得、SSH サーバ、Taildrop、Kubernetes 連携、AWS SDK。**全部入りだと数十 MB になる。**

そこで **機能ごとにビルドタグを用意し、不要なものを外せる** ようにした。

```sh
go build -tags ts_omit_acme,ts_omit_ssh,ts_omit_taildrop ./cmd/tailscaled
```

### 機能の一覧が 1 か所にある

`feature/featuretags/featuretags.go` に、**84 個の機能がマップとして定義されている**。

```go
var Features = map[FeatureTag]FeatureMeta{
	"acme":  {Sym: "ACME", Desc: "ACME TLS certificate management"},
	"advertiseexitnode": {
		Sym:  "AdvertiseExitNode",
		Desc: "Run an exit node",
		Deps: []FeatureTag{"peerapiserver", "advertiseroutes"},
	},
	...
}
```

**依存関係も宣言されている。** 「exit node を動かすには peerAPI サーバと経路広告が要る」。

### そこから 2 種類のファイルが生成される

1. **`buildfeatures` パッケージの const** — `HasACME` という真偽値
2. **`condregister` パッケージの blank import** — 機能パッケージをリンクする

const にするのが要点で、**Go のコンパイラが `if false { ... }` を dead code として除去する**。

### 実行時の登録と、コンパイル時の定数を区別する

- **`buildfeatures.HasACME`** — コンパイル時。バイナリに含まれているか
- **`feature.IsRegistered("acme")`** — 実行時。init が走ったか

**含まれているが import されていない** ことがある。[tsnet](../tsnet/) は多くの機能を意図的に import しない。

## ソースコードのどこか

### 機能の定義

```go title="feature/featuretags/featuretags.go"
// FeatureMeta describes a modular feature that can be conditionally linked into
// the binary.
type FeatureMeta struct {
	Sym  string       // exported Go symbol for boolean const
	Desc string       // human-readable description
	Deps []FeatureTag // other features this feature requires

	// ImplementationDetail is whether the feature is an internal implementation
	// detail. That is, it's not something a user would care about having or not
	// having, but we'd like to able to omit from builds if no other
	// user-visible features depend on it.
	ImplementationDetail bool
}
```

[`featuretags.go#L78-L90`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/feature/featuretags/featuretags.go#L78-L90)。

**`ImplementationDetail` が興味深い。** 「ユーザーが有無を気にするものではないが、それに依存するユーザー可視の機能がなければビルドから外したい」。

たとえば `c2n` は、ユーザーから見れば機能ではない。だが **[経路広告](../subnet-router-exit-node/)が依存している** ので、経路広告を使うなら含まれる。使わなければ消える。

**「機能」と「機能を支える部品」を同じ仕組みで管理しつつ、UI での見せ方だけを分けている。**

### 依存関係の解決

```go title="feature/featuretags/featuretags.go"
func Requires(ft FeatureTag) set.Set[FeatureTag] {
	s := set.Set[FeatureTag]{}
	var add func(FeatureTag)
	add = func(ft FeatureTag) {
		s.Add(ft)
		for _, dep := range Features[ft].Deps {
			add(dep)
		}
	}
	add(ft)
	return s
}

// RequiredBy is the inverse of Requires: it returns the set of features that
// depend on the given feature (directly or indirectly), including the feature
// itself.
func RequiredBy(ft FeatureTag) set.Set[FeatureTag] {
	s := set.Set[FeatureTag]{}
	for f := range Features {
		if featureDependsOn(f, ft) {
			s.Add(f)
		}
	}
	return s
}
```

[`featuretags.go#L38-L63`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/feature/featuretags/featuretags.go#L38-L63)。

**両方向の依存が引ける。**

- **`Requires`** — 「この機能を含めるなら、他に何が要るか」
- **`RequiredBy`** — 「この機能を外すと、何が壊れるか」

後者があることで、**「`ts_omit_c2n` を指定したが、経路広告も使っている」という矛盾を検出できる**。

依存の解決は素朴な再帰だ。**84 個の機能では、これで十分速い。** 循環参照があれば無限再帰するが、**そもそも循環を作らないという前提**で書かれている。

### 定数の生成

```go title="feature/buildfeatures/buildfeatures.go"
//go:generate go run gen.go

// Package buildfeatures contains boolean constants indicating which features
// were included in the binary (via build tags), for use in dead code
// elimination when using separate build tag protected files is impractical or
// undesirable.
package buildfeatures
```

```go title="feature/buildfeatures/feature_acme_enabled.go"
// Code generated by gen.go; DO NOT EDIT.

//go:build !ts_omit_acme

package buildfeatures

// HasACME is whether the binary was built with support for modular feature "ACME TLS certificate management".
// Specifically, it's whether the binary was NOT built with the "ts_omit_acme" build tag.
// It's a const so it can be used for dead code elimination.
const HasACME = true
```

[`buildfeatures.go#L4-L10`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/feature/buildfeatures/buildfeatures.go#L4-L10)。

**機能ごとに 2 つのファイルが生成される** — `_enabled.go` (`!ts_omit_acme` のとき) と `_disabled.go` (`ts_omit_acme` のとき)。84 個 × 2 = 168 ファイル。

**なぜ `var` ではなく `const` なのか。**

```go
if buildfeatures.HasACME {
	// 大量のコード
}
```

`const` が `false` なら、**Go のコンパイラはこのブロックを削除する**。そして中で呼ばれている関数が他から呼ばれていなければ、**その関数もリンクされない**。連鎖的に消える。

`var` だと実行時の値なので、コンパイラは消せない。

**「ビルドタグでファイルを分ける」が現実的でない場所** — 関数の途中、条件分岐の中 — では、この const が使われる。

### 条件付きの登録

```go title="feature/condregister/condregister.go"
// Package condregister registers all conditional features guarded by build
// tags. It is one central package that callers can empty import to ensure all
// conditional features are registered.
package condregister

import (
	// Portmapper is special in that the CLI also needs to link it in,
	// so it's pulled out into its own package, rather than using a maybe_*.go
	// file in condregister.
	_ "tailscale.com/feature/condregister/portmapper"

	// HTTP proxy support is also needed by the CLI, and tsnet, so it's its
	// own package too.
	_ "tailscale.com/feature/condregister/useproxy"
)
```

```go title="feature/condregister/maybe_acme.go"
//go:build !js && !ts_omit_acme

package condregister

import _ "tailscale.com/feature/acme"
```

[`condregister.go`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/feature/condregister/condregister.go) と [`maybe_acme.go`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/feature/condregister/maybe_acme.go)。

**`maybe_*.go` が各 1 ファイル、中身は blank import 1 行。** ビルドタグが条件を表す。

`tailscaled` は `condregister` を 1 回 import するだけで、**そのビルドに含まれるすべての機能がリンクされる**。

`js` (WebAssembly) を除外しているのも、**プラットフォームによる条件と機能による条件を同じ行で表現している**。

**例外が 2 つある** — portmapper と HTTP プロキシは、CLI や tsnet からも必要なので独立したパッケージになっている。**「なぜ例外なのか」がコメントで説明されている。**

### フックの仕組み

```go title="feature/feature.go"
// Package feature tracks which features are linked into the binary.
package feature

var ErrUnavailable = errors.New("feature not included in this build")

// IsRegistered reports whether the named feature package's init
// function has run and registered itself via [Register] in this
// binary. It is distinct from the compile-time [buildfeatures]
// constants: a feature package can be present in the binary but not
// imported (e.g. tsnet deliberately does not import many features),
// in which case its init does not run.
func IsRegistered(name string) bool { return in[name] }

// Register notes that the named feature is linked into the binary.
func Register(name string) {
	if _, ok := in[name]; ok {
		panic("duplicate feature registration for " + name)
	}
	in[name] = true
}
```

[`feature.go#L4-L35`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/feature/feature.go#L4-L35)。

**「コンパイル時の定数」と「実行時の登録」の違いが、コメントで明示されている。**

`buildfeatures.HasACME` が true でも、**その機能パッケージが import されていなければ init は走らない**。[tsnet](../tsnet/) は多くの機能を意図的に import しないので、この区別が必要になる。

```go title="feature/feature.go"
// Hook is a func that can only be set once.
//
// It is not safe for concurrent use.
type Hook[Func any] struct {
	f  Func
	ok bool
}

// Set sets the hook function, panicking if it's already been set
// or f is the zero value.
//
// It's meant to be called in init.
func (h *Hook[Func]) Set(f Func) {
	if h.ok {
		panic("Set on already-set feature hook")
	}
```

[`feature.go#L37-L57`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/feature/feature.go#L37-L57)。

**「並行アクセスに対して安全でない」と明記されている。** `init()` の中で呼ばれる前提なので、ミューテックスが要らない。

**Go の `init()` は、パッケージの依存順に、単一 goroutine で実行される** ことが保証されている。この保証に乗ることで、同期のコストがゼロになる。

そして **二重設定は panic**。[c2n](../c2n/)、[peerAPI](../peerapi/) と同じ、起動時に必ず落ちる形だ。

### 使う側の書き方

機能が無効なときの振る舞いは、3 通りある。

```go
// 1. 定数で分岐する (dead code elimination が効く)
if buildfeatures.HasDNS {
	...
}

// 2. フックが設定されていれば呼ぶ
if f, ok := HookCanAutoUpdate.GetOk(); ok {
	return f()
}
return false

// 3. エラーを返す
if !buildfeatures.HasPeerAPIServer {
	http.Error(w, feature.ErrUnavailable.Error(), http.StatusNotImplemented)
	return
}
```

**「静かに無効」「既定値を返す」「エラーにする」を、機能の性質で使い分けている。**

`ErrUnavailable` という共通のエラーがあるので、**呼び出し側が「機能がない」ことを判別できる。**

### 補助的な const パッケージ

```go title="omit/omit.go"
// Package omit provides consts to access Tailscale ts_omit_FOO build tags.
// They're often more convenient to eliminate some away locally with a const
// rather than using build tags.
package omit

// Err is an error that can be returned by functions in this package.
var Err = errors.New("feature not linked into binary per ts_omit build tag")
```

[`omit.go`](https://github.com/tailscale/tailscale/blob/1e69418c298b680562a2fecd7020f7f58d17d166/omit/omit.go)。

**`buildfeatures` とは別に、`omit` パッケージがある。** こちらは「ビルドタグを const として見る」だけの薄い層で、`buildfeatures` の生成対象になっていない機能 (AWS など) に使われる。

**「ビルドタグでファイルを分けるより、const で局所的に消すほうが便利なことが多い」** という動機がドキュメントに書かれている。

## なぜそうなっているか

### なぜ const にするのか

Go のコンパイラは、**コンパイル時に false と分かる条件分岐を削除する**。そして到達不能になった関数は、リンカが除去する。

```go
if buildfeatures.HasACME {  // const false
	cert, err := getCert(domain)  // このコードは消える
	...
}
```

`getCert` が他から呼ばれていなければ、**その関数も、それが呼ぶ ACME ライブラリも、全部消える**。

**`var` だとこれが起きない。** 実行時に値が変わりうるので、コンパイラは両方の分岐を残す。

**1 文字の違い (`const` か `var` か) が、バイナリサイズの数 MB を分ける。**

### なぜビルドタグだけでは足りないのか

ビルドタグは **ファイル単位** でしか効かない。

「この関数の中の、この 10 行だけを消したい」という場合、

- **ファイルを分割する** — 関数を 2 つのファイルに分け、片方にタグを付ける。**構造が壊れる**
- **const で分岐する** — その場に書ける

`buildfeatures` の const は、**ビルドタグの粒度の粗さを補う** ためにある。パッケージのドキュメントが「ビルドタグで保護されたファイルを分けるのが非現実的または望ましくない場合の dead code elimination のため」と書いているとおりだ。

### なぜ機能の一覧を 1 か所に集めるのか

84 個の機能が散らばっていると、

- **どんなタグがあるか分からない**。`grep ts_omit_` で探すしかない
- **依存関係が分からない**。「これを外すと何が壊れるか」
- **ドキュメントが書けない**

マップとして 1 か所にあれば、

- **CLI が一覧を表示できる**
- **依存の検証ができる**。矛盾する組み合わせを検出する
- **コード生成の入力になる**。168 個のファイルが自動で作られる

**「宣言的なデータを 1 か所に置き、そこから生成する」** は、Tailscale が [netmap の View](../codegen-views/) でも使っている形だ。

### なぜコンパイル時と実行時を区別するのか

**「バイナリに含まれている」と「初期化された」は別のこと** だ。

[tsnet](../tsnet/) は、ライブラリとして使われる。利用者のバイナリに何が入るかは、利用者の import 次第だ。

- **`buildfeatures.HasSSH == true`** — SSH のコードはビルドに含まれうる
- **`feature.IsRegistered("ssh") == false`** — だが利用者が import していないので、init は走っていない

この区別がないと、**「機能があるはずなのに動かない」という混乱**が起きる。だから 2 つの問い合わせ方法を用意し、**違いをドキュメントに書いている**。

### なぜ init での設定に同期が要らないのか

Go の仕様は、**パッケージの初期化が単一の goroutine で、依存順に行われる** ことを保証している。

- パッケージ A が B を import していれば、B の `init()` が先に走る
- **すべての `init()` が終わってから `main()` が始まる**
- **`init()` の実行中に他の `init()` が並行に走ることはない**

だから **フックの設定にミューテックスが要らない**。

`Hook` のドキュメントに「並行アクセスに対して安全でない」と書いてあるのは、**この前提を明示するため**だ。誰かが `init()` 以外から `Set` を呼ぶと壊れる。

**言語仕様が保証する前提に乗ることで、同期のコストと複雑さを避けている。**

### なぜ「実装の詳細」というフラグがあるのか

`c2n` や `peerapiserver` は、ユーザーから見れば機能ではない。「c2n を有効にしますか?」と聞かれても答えられない。

だが **ビルドから外せると嬉しい**。誰も使わないなら、コードがない方がよい。

`ImplementationDetail: true` を付けると、

- **UI や CLI の機能一覧に出さない**
- **依存関係の解決には参加する**

**「内部的な部品も同じ仕組みで管理するが、ユーザーには見せない」** という区別を、フィールド 1 つで表現している。

### なぜ例外パッケージがあるのか

`condregister` は `tailscaled` 用だ。だが portmapper と HTTP プロキシは、**CLI (`tailscale netcheck`) や [tsnet](../tsnet/) からも必要になる**。

`condregister` を CLI から import すると、**全機能がリンクされてしまう**。CLI のバイナリが `tailscaled` と同じサイズになる。

だから **その 2 つだけ、独立した小さなパッケージに切り出す**。CLI はそれだけを import する。

**「1 つの登録点にまとめる」という設計に、例外が 2 つある。** そして **なぜ例外なのかがコメントで説明されている** — これがないと、後から「統一すべきでは」と直される。

## どう活かすか

**バイナリサイズが問題になる可能性があるなら、機能の境界を早めに設計する。** 後から分離するのは、依存が絡み合った後では非常に難しい。**「この機能を外せるか」を問い続けると、結合が緩く保たれる。**

**dead code elimination を効かせるには `const` を使う。** `var` では効かない。1 文字の違いがバイナリサイズを分ける。**生成コードでこれを担保する** と、書き間違いがなくなる。

**ビルドタグはファイル単位でしか効かないので、const と組み合わせる。** 「関数の中の 10 行だけを消す」にはファイル分割が不自然になる。**両方の道具を持ち、使い分ける基準を書く。**

**機能の一覧は、宣言的なデータとして 1 か所に置く。** 依存関係も含める。そこから定数、登録ファイル、ドキュメント、CLI の一覧が生成できる。**散らばったビルドタグは、grep でしか見つからない。**

**依存は両方向に引けるようにする。** 「これを含めるには何が要るか」と「これを外すと何が壊れるか」。後者があると、矛盾する設定を検出できる。

**「コンパイル時に含まれているか」と「実行時に初期化されたか」を区別する。** ライブラリとして提供する場合、利用者の import 次第で後者が変わる。**両方を問い合わせる手段を用意し、違いをドキュメントに書く。**

**Go の `init()` の順序保証に乗ると、同期が不要になる。** 「単一 goroutine で、依存順に、main の前に」という保証は強力だ。**乗るなら「並行アクセスには安全でない」と明記して、前提を守らせる。**

**設計に例外を作るなら、なぜ例外なのかをその場に書く。** 「1 つの登録点にまとめる」原則の例外が 2 つあるなら、その 2 つに理由を書く。書かないと統一されて壊れる。
