## 何を学んだか

### 3 つの設計判断

WireGuard は 2016 年に登場した VPN プロトコルで、既存の VPN (IPsec、OpenVPN) と比べて次の点が違う。

**1. 暗号アルゴリズムを選ばせない。** ネゴシエーションがない。使うものが固定されている。

| 用途           | アルゴリズム             |
| -------------- | ------------------------ |
| 鍵交換         | Curve25519 (ECDH)        |
| 暗号化         | ChaCha20-Poly1305 (AEAD) |
| ハッシュ       | BLAKE2s                  |
| 鍵導出         | HKDF                     |
| ハンドシェイク | Noise_IKpsk2             |

TLS や IPsec には「暗号スイートの交渉」があり、**そこが脆弱性の温床になってきた** (ダウングレード攻撃、弱い組み合わせの選択)。WireGuard は交渉自体をなくした。**アルゴリズムを変えるときは、プロトコルのバージョンごと変える。**

**2. 設定が公開鍵と IP 範囲だけ。**

```ini
[Interface]
PrivateKey = <自分の秘密鍵>
Address    = 10.0.0.1/24

[Peer]
PublicKey  = <相手の公開鍵>
AllowedIPs = 10.0.0.2/32
Endpoint   = 203.0.113.5:51820
```

証明書も、CA も、ユーザー名も、パスワードもない。**「この公開鍵の相手は、この IP 範囲を担当する」** という対応表がすべてだ。

**3. UDP 1 本しか使わない。** 制御用のチャネルもなく、TCP へのフォールバックもない。パケットは 4 種類だけ。

### 何をしないか

そしてここが Tailscale の存在理由になる。

| 必要なこと                | WireGuard              | 誰がやるか                                   |
| ------------------------- | ---------------------- | -------------------------------------------- |
| パケットの暗号化          | **やる**               | WireGuard                                    |
| 相手の認証                | **やる**               | WireGuard (公開鍵)                           |
| 経路が変わったときの追随  | **やる** (ローミング)  | WireGuard                                    |
| **相手の公開鍵を知る**    | やらない               | [control server](../netmap/)                 |
| **相手の IP:port を知る** | やらない               | [magicsock + disco](../disco-protocol/)      |
| **NAT を越える**          | やらない               | [netcheck / portmapper / DERP](../netcheck/) |
| **アクセス制御**          | やらない (IP 範囲のみ) | [ACL / パケットフィルタ](../packet-filter/)  |

**WireGuard の設定ファイルには `Endpoint = 203.0.113.5:51820` と書く。** この値をどこから持ってくるかは、WireGuard の関心事ではない。

手で書くなら固定 IP を持つサーバが要る。**両側が NAT の内側にいる場合、書くべき値が存在しない。**

## プロトコルと設定のかたち

### パケットは 4 種類

```go
MessageInitiationType  = 1  // ハンドシェイク開始 (148 バイト固定)
MessageResponseType    = 2  // ハンドシェイク応答 (92 バイト固定)
MessageCookieReplyType = 3  // 負荷時の DoS 対策
MessageTransportType   = 4  // 実データ
```

**ハンドシェイクは 1 往復で完了する。** 開始と応答の 2 メッセージで、双方がセッション鍵を得る。

そして **サイズが固定** だ。148 バイトと 92 バイト。パケット長から「何のメッセージか」が推測できてしまうが、代わりに **パースが単純になり、増幅攻撃の余地がなくなる**。

データパケットの構造も単純だ。

```go
type MessageTransport struct {
	Type     uint32  // 4
	Receiver uint32  // 相手が割り当てたセッション ID
	Counter  uint64  // nonce として使うカウンタ
	Content  []byte  // 暗号化されたペイロード + 16 バイトの認証タグ
}
```

**ヘッダ 16 バイト + タグ 16 バイト = 32 バイトのオーバーヘッド。** IP と UDP のヘッダを足すと、[Tailscale が MTU の計算に使う 80 バイト](../peer-mtu/) になる。

`Receiver` が「相手が割り当てたセッション ID」なのが要点だ。**公開鍵は載らない。** 誰宛かはこの 4 バイトで決まるので、受信側はセッション ID から鍵を引く。**復号する前に公開鍵の照合をしない** ので、処理が速い。

### AllowedIPs が 2 つの意味を持つ

`AllowedIPs` は WireGuard で最も重要かつ紛らわしい設定だ。**送信と受信で別の意味を持つ。**

**送信時**: 「この宛先 IP のパケットは、このピアに送る」というルーティングテーブル。最長一致で選ぶ。

**受信時**: 「このピアから来たパケットの送信元 IP は、この範囲でなければならない」というフィルタ。範囲外なら捨てる。

WireGuard はこれを **cryptokey routing** と呼ぶ。「暗号鍵とIP範囲の対応が、そのままルーティング表になる」という意味だ。

**受信側のフィルタが重要だ。** これがないと、あるピアが「自分は 10.0.0.99 だ」と偽って別のピアになりすませる。**IP アドレスの詐称が、公開鍵と IP 範囲の対応によって防がれている。**

wireguard-go では、この対応表は **基数木 (trie)** で実装されている。数千のピアがいても、最長一致が高速に引ける。

Tailscale では、この `AllowedIPs` が [netmap の `Node.AllowedIPs`](../netmap/) から来る。[subnet router や exit node](../subnet-router-exit-node/) は、この範囲が広いだけのピアだ。

### タイマーで駆動する

WireGuard には「接続」の概念がない。**状態はタイマーで管理される。**

| 定数                  | 値            | 意味                                                     |
| --------------------- | ------------- | -------------------------------------------------------- |
| `RekeyAfterTime`      | 120 秒        | この時間が経ったら鍵を作り直す                           |
| `RejectAfterTime`     | 180 秒        | この時間を過ぎた鍵は使えない                             |
| `RekeyTimeout`        | 5 秒          | ハンドシェイクの応答を待つ時間                           |
| `KeepaliveTimeout`    | 10 秒         | データを受けた後、この時間で応答がなければキープアライブ |
| `RekeyAfterMessages`  | 2⁶⁰           | この数のメッセージを送ったら鍵を作り直す                 |
| `RejectAfterMessages` | 2⁶⁴ − 2¹³ − 1 | この数を超えた鍵は使えない                               |

**時間とメッセージ数の両方に上限がある。** ChaCha20-Poly1305 の nonce は 64 ビットのカウンタなので、使い切る前に鍵を替える必要がある。2⁶⁰ は「まず到達しないが、理論上の上限より十分手前」の値だ。

`RekeyAfterTime` (120) < `RejectAfterTime` (180) の 60 秒の余裕が、**再ハンドシェイクが失敗しても数回リトライできる時間** になっている。

そして **ハンドシェイクを開始できるのは、データを送りたい側だけ** だ。受け取る側から要求はできない。「送るものがなければ、鍵を作り直す必要もない」という考え方になっている。

### ローミング

WireGuard は、**ピアから来たパケットの送信元アドレスを見て、そのピアの `Endpoint` を更新する**。

だから携帯端末が Wi-Fi から LTE に切り替わっても、**接続が切れない**。新しいアドレスから正しく認証されたパケットが来れば、そちらに返すようになる。

これが成立するのは、**認証が公開鍵とセッション鍵で行われ、IP アドレスに依存していない** からだ。「どこから来たか」は識別に使われない。

**Tailscale の [経路切り替え](../derp-to-direct/) は、この性質の上に成り立っている。** magicsock が送信先を変えても、WireGuard から見れば「ピアがローミングした」だけになる。

### リプレイ攻撃への対処が 2 段

**データパケット**: `Counter` を見て、スライディングウィンドウで重複を検出する。既に受け取ったカウンタなら捨てる。

**ハンドシェイク**: 開始メッセージに **TAI64N 形式のタイムスタンプ** が暗号化されて入る。受信側は「そのピアから最後に受け取ったタイムスタンプより後」でなければ拒否する。

タイムスタンプ方式には、**状態をほとんど持たなくてよい** という利点がある。ピアごとに「最後に見たタイムスタンプ」を 12 バイト覚えるだけで、過去のハンドシェイクの再送を全部弾ける。

### DoS 対策の cookie

ハンドシェイクの開始メッセージには、末尾に `MAC1` と `MAC2` という 2 つの認証子が付く。

- **`MAC1`** — 受信者の公開鍵から計算される。**公開鍵を知らない相手からのパケットを、暗号処理の前に捨てられる**
- **`MAC2`** — 負荷が高いときだけ検証される。サーバが cookie を返し、クライアントがそれを含めて再送する

`MAC1` の効果が大きい。**サーバの公開鍵を知らないスキャナからのパケットは、BLAKE2s の計算 1 回で捨てられる。** Curve25519 のスカラー倍算 (3 桁遅い) まで到達しない。

**[disco が「知っている鍵か」を先に見る](../disco-protocol/) のと同じ発想** で、安い検査を前に置いている。

`MAC2` の cookie は、**送信元 IP に紐づく** ため、アドレスを詐称した相手は正しい cookie を得られない。[peer relay のバインド](../peer-relay/) が MAC で同じことをしているのは、この設計の踏襲だ。

### パディング

送信するパケットは、**16 バイトの倍数になるようにパディングされる** (`PaddingMultiple = 16`)。

パケット長から中身を推測されにくくするための措置だ。完全な防御ではないが、コストがほぼゼロなので入っている。

## なぜそうなっているか

### なぜ暗号の選択肢をなくすのか

TLS や IPsec の脆弱性の多くは、**アルゴリズムそのものではなく、その選択と交渉** から来ている。

- **ダウングレード攻撃** — 中間者が弱い暗号を選ばせる
- **実装の組み合わせ爆発** — 対応する暗号スイートの数だけコードパスが増える
- **古い設定が残る** — 一度サポートしたものを消せない

WireGuard は **「今の時点で最良と考えられるものを 1 つ選び、それだけを実装する」** ことにした。

代償は明白だ。**その暗号が破られたら、プロトコルごと乗り換えるしかない。** だが「暗号の危殆化は、交渉可能にしても結局は移行が必要」という判断がある。そして **交渉をなくしたぶん、実装が桁違いに小さくなる** — Linux カーネルの実装は約 4,000 行で、IPsec の数万行と比べて監査が現実的な規模になった。

Tailscale が [control プロトコルにも Noise を選んだ](../noise-transport/) のは、同じ判断の踏襲だ。

### なぜ設定に Endpoint を書くのか

WireGuard の設計思想は **「カーネルのネットワークインターフェースとして振る舞う」** ことだ。`wg0` は `eth0` と同じように扱える。

インターフェースは「どこに送るか」を知っている必要がある。だが **「どこにいるかを探す」のは、インターフェースの仕事ではない**。

そして **手で設定できる範囲では、これで十分だった**。データセンター間のトンネル、固定 IP のサーバへの VPN。片側が固定 IP を持てば、もう片側は NAT の内側でも動く (先に送れば、ローミングで相手が学習する)。

**両側が NAT の内側にいる場合だけが解けない。** そしてそれが、個人のデバイス同士を繋ぐときの標準的な状況になる。

**Tailscale はこの 1 点を埋めるために作られた** と言ってよい。[magicsock](../magicsock/) が `conn.Bind` を実装し、`Endpoint` を動的に決める。

### なぜ「接続」がないのか

WireGuard には `connect` も `accept` もない。**設定した瞬間からピアは存在し、送るものがあれば送る。**

これには実務的な利点がある。

- **プロセスの再起動で状態が失われない**。設定さえあれば、次のパケットでハンドシェイクが走る
- **アイドル時のコストがゼロ**。`PersistentKeepalive` を設定しない限り、何も流れない
- **「切れた」という状態を扱わなくてよい**。届かなければ再ハンドシェイクするだけ

**タイマー駆動なので、状態機械が小さい。** ハンドシェイク中か、鍵を持っているか、期限切れか。それだけだ。

Tailscale が [endpoint の信頼に期限を持たせている](../endpoint-selection/) のも、同じ発想と言える。「接続」という状態を作らず、時間で劣化させる。

### なぜ AllowedIPs が受信フィルタも兼ねるのか

ルーティングと認可を分けると、設定が 2 つになる。

- 「10.0.0.2 宛はピア A へ」(ルーティング)
- 「ピア A は 10.0.0.2 を名乗ってよい」(認可)

**この 2 つがずれると、なりすましが成立する。** ピア A が「自分は 10.0.0.3 だ」と言えるなら、10.0.0.3 宛の通信を横取りできる。

**1 つの設定にすれば、ずれようがない。** そして意味も直感的になる — 「このピアはこの範囲を担当する」。

代償は **柔軟性** だ。「送信は許すが受信は許さない」といった非対称な設定ができない。Tailscale が [別途パケットフィルタを持つ](../packet-filter/) のは、より細かい制御 (ポート単位、方向) が必要だからだ。

### なぜ MAC1 があるのか

インターネットに UDP ポートを開けると、**スキャンのパケットが飛んでくる**。

ハンドシェイクの開始メッセージを受け取るたびに Curve25519 の計算をすると、**それだけで CPU が飽和する**。1 パケットあたり数十マイクロ秒なので、秒間数万パケットで 1 コアが埋まる。

`MAC1` は **受信者の公開鍵をキーにした BLAKE2s** なので、公開鍵を知らない相手は作れない。そして検証は数百ナノ秒で終わる。

**「正当な相手であることの安い証明」を先に要求する** という構造で、DTLS の HelloVerifyRequest、QUIC の Retry、SYN cookie と同じ系譜にある。

## どう活かすか

**プロトコルに交渉を入れるかは、慎重に決める。** 暗号スイート、圧縮方式、バージョン。交渉可能にすると柔軟だが、**ダウングレード攻撃と実装の組み合わせ爆発を招く**。「1 つに固定し、変えるときはプロトコルごと変える」は、実装の小ささと監査可能性を買う選択だ。

**ルーティングと認可を 1 つの設定にまとめられないか考える。** 分けると、ずれたときになりすましが成立する。「この主体はこの範囲を担当する」という 1 つの宣言で両方を表現できるなら、設定ミスの余地が消える。

**「接続」という状態を作らず、タイマーで管理する形がある。** 状態機械が小さくなり、再起動やパケットロスからの回復が自動になる。**「切れた」を検知して対処するより、「一定時間で失効する」ほうが単純だ。**

**認証を IP アドレスから切り離すと、ローミングが無料で手に入る。** 「どこから来たか」を識別に使わなければ、送信元が変わっても通信が続く。モバイル環境では決定的な差になる。

**暗号処理の前に、安い検査を置く。** 公開鍵を知っている相手だけが作れる MAC を要求すれば、スキャンのパケットを 3 桁安く捨てられる。**インターネットに口を開けるサービスでは、ほぼ必須の構造。**

**「何をしないか」を明確にすると、周辺のソフトウェアが育つ。** WireGuard は経路探索も鍵配布もしない。だからこそ Tailscale や他の実装が、それぞれのやり方でその層を埋められた。**やることを絞ったプロトコルは、組み合わせの部品になれる。**
