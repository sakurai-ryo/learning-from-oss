Tokio は Rust の非同期ランタイムだ。`async`/`await` で書いたコードを実際に動かす土台で、スレッドプール・I/O の待ち受け・タイマー・同期プリミティブまでを 1 つのクレートで提供している。

Rust で非同期のサーバやクライアントを書くと、直接使っていなくてもほぼ確実に依存関係に入っている。**「Rust の非同期」がどう動くかを知ることは、事実上 Tokio がどう動くかを知ることに近い。**

## この OSS について

- MIT ライセンス。`tokio` 本体は `tokio/src/` でテストを除くと約 10.6 万行、378 ファイル。統合テストが別に約 3.5 万行ある。
- **`unsafe` がソース中に 1000 箇所以上ある。** 侵入型の連結リスト、型消去した vtable、`MaybeUninit` の配列、自前で計算したフィールドのオフセット。ライブラリの性質上避けられないもので、**その代わり安全性の根拠がほぼすべてコメントに書かれている**。この章の引用の多くは、その `// Safety:` コメントそのものになる。
- **状態はとにかく 1 語のアトミック変数に詰め込まれる。** タスクのライフサイクルと参照カウント、実行キューの 2 つのインデックス、ソケットの readiness と世代番号、待機中ワーカーの人数と探索中の人数。「複数の値を同時に、不可分に更新したい」という要求が、そのままビットパックとして現れている。
- **速くするための仕掛けには、必ず打ち切り条件が付いている。** 局所性のための LIFO スロットは連続 3 回まで、グローバルキューは N 回に 1 回必ず覗く、探索中のワーカーは半数まで、1 回の poll の予算は 128 操作まで。**「速くすると誰かが飢える」を毎回セットで考えている** のが、この章を通して見えてくる。
- **定数の根拠が正直に書かれている。** 「値は何もないところから引っ張ってきた (plucked out of thin air)」というコメントが複数ある。もっともらしい説明を捏造せず、測定して変えられる余地を残している。
- **並行性の検証に、際立った投資がある。** ソースは `std::sync` をほぼ直接使わず、`crate::loom::sync` を経由する。`--cfg loom` でビルドすると全部がモデル検査ツールの実装に差し替わり、**可能な実行順序を全部試す**。そのために `UnsafeCell` へのアクセスまでクロージャ渡しの API に統一されていて、本番ビルドではゼロコストになる。

## 読む順番

非同期ランタイムの内部に馴染みがない場合は、[前提のページ](./architecture/) から読んでほしい。Future・Waker・task・scheduler・driver・park・readiness・budget といった語彙を、普通のスレッドプールとの対応で全部ここで導入する。

「タスクの表現」の 5 ページは前から順に読むのがよい。特に最初の [状態のページ](./task-state/) は、他のほぼ全ページから参照される。

「work-stealing スケジューラ」も前から順に読むと、キューの構造 → 溢れたときの扱い → 局所性の最適化 → 起床の判断、という 1 本の流れになる。

「ドライバ」は独立して読めるが、キャンセル安全性のページ (15) は readiness のページ (14) を前提にしている。

[loom のページ](./loom-model-checking/) は Tokio 固有の知識をほとんど要求しないので、そこから読み始めてもいい。他のページに繰り返し出てくる `with_mut(|ptr| ...)` や「検査モードでは定数を小さくする」が何のためにあるかが分かる。
